# SPEC: guarded-exchange-mcp

Статус: **после grilling и Explore + Plan (2026-10-27)**, PLAN утверждён, следующий шаг — grilling PLAN и тикеты. Документ отвечает на вопрос «что система должна делать», а не «как». Технические решения — в `PLAN.md`. Решения интервью и grilling — в разделе 10; новые требования, появившиеся на grilling, получили номера FR-41+ (чтобы не ломать ссылки), но стоят в своих тематических разделах.

## 1. Суть
MCP-сервер, который даёт AI-агентам (Claude Desktop, Claude Code, собственные агенты) безопасный доступ к криптобирже: чтение рынка и аккаунта, торговля на споте и линейных перпетуалах. Главная ценность — не «обёртка над API», а **ограждения**: права по принципу least-privilege, риск-лимиты, подтверждение человеком рискованных действий в канале, который модель не контролирует, изоляция пользователей, полный журнал действий.

Портфельная цель: показать на интервью MCP поверх существующего REST API с auth, multi-tenancy, rate limits, error handling, human-in-the-loop, audit log — и измерение качества AI-части (evals выбора инструментов).

## 2. Акторы и границы доверия
- **Админ** — оператор сервера. Создаёт пользователей, выдаёт доступ, задаёт потолок прав и лимитов, включает mainnet для конкретного пользователя, может включить kill switch для любого пользователя. Действует только через служебный канал (CLI), не через MCP.
- **Пользователь (tenant)** — трейдер. Подключает своего AI-клиента к серверу, сам добавляет ключи биржи, может ужесточить свою политику (но не выйти за потолок админа), подтверждает рискованные действия, читает свой журнал, может включить свой kill switch.
- **Модель (LLM-агент)** — от имени пользователя вызывает инструменты. **Всегда недоверенная сторона:** может ошибаться, зацикливаться, быть жертвой prompt injection. Ничто, что модель может сделать вызовом инструмента или текстом, не является подтверждением человека.
- **Программа AI-клиента** (Claude Desktop, Claude Code, наш консольный агент, чужой самописный клиент) — **доверие условное.** Подтверждение через UI клиента (elicitation) сервер не может отличить от автоматического ответа самописного клиента. Поэтому доверять ли UI-подтверждению программы клиента — настройка политики (FR-42); внешний канал подтверждения считается доверенным всегда.
- **Биржа** — внешняя система с собственными лимитами и правилами инструментов. Текстовые данные с биржи (и из истории/журнала) — недоверенные данные.

Допущение: биржевой аккаунт (или сабаккаунт), чьи ключи добавлены, целиком принадлежит пользователю. Рекомендуется выделенный сабаккаунт; на аккаунте могут быть ордера и позиции, созданные не через систему (вручную, другими ботами).

## 3. Режимы работы
- **Локальный:** один пользователь, сервер запускается на его машине и подключается к Claude Desktop/Code. Админ и пользователь — одно лицо, настройка через конфиг/CLI. Политики, лимиты, подтверждения и журнал работают так же, как в удалённом режиме.
- **Удалённый (multi-tenant):** сервис по сети, много пользователей, каждый аутентифицирован, у каждого свои ключи биржи, политика и журнал.

Термин: **testnet** в этом документе — тестовая среда биржи без реальных денег (для выбранной биржи Bybit — Demo Trading; классический testnet — запасной вариант), **mainnet** — реальная торговля.

## 4. Функциональные требования

### 4.1 Чтение (никогда не требует подтверждения)
- FR-1. Рыночные данные: текущая цена и сводка по инструменту, стакан, свечи, правила инструмента (шаг цены, минимальный и шаг объёма, максимальное плечо).
- FR-2. Аккаунт: балансы, открытые позиции (перпетуалы), открытые ордера, история ордеров и сделок за период. Ордера и позиции помечены происхождением: «создан через систему» или «внешний».
- FR-3. Ответы пригодны для LLM: компактные, с единицами измерения, без лишних полей, с пагинацией/ограничением объёма для больших списков.
- FR-41. Свободные текстовые поля из внешних источников (биржа, история, журнал) в ответах явно помечены как недоверенные данные, а не инструкции. Сервер не обещает обнаруживать prompt injection; защита от её последствий — права, лимиты и подтверждение человеком, которые действуют на любое изменяющее действие независимо от того, что его вызвало. Устойчивость модели к injection измеряется evals (FR-40).

### 4.2 Торговые действия
- FR-4. Разместить ордер (market, limit) на споте и перпетуалах; для перпетуалов — reduce-only. В v1 — только инструменты с котировкой в USDT.
- FR-5. Изменить и отменить ордер; отменить все ордера по инструменту. Действует на любые ордера аккаунта, включая внешние (запрос подтверждения показывает, что затронуты внешние ордера).
- FR-6. Установить или изменить stop-loss / take-profit позиции — **только перпетуалы.**
- FR-7. Закрыть позицию (полностью или частично) — **только перпетуалы.**
- FR-8. Изменить плечо по инструменту.
- FR-9. **Вне scope навсегда:** вывод средств, переводы между аккаунтами/кошельками, управление ключами биржи через AI-клиента.
- FR-10. Перед отправкой на биржу параметры проверяются на соответствие правилам инструмента (шаг цены, объёма, минимумы); нарушение — понятная ошибка с подсказкой, как исправить, без обращения к бирже.
- FR-43. Каждое торговое действие классифицируется как **увеличивающее риск** (новый ордер не reduce-only, увеличение плеча, изменение ордера в сторону большего объёма или менее выгодной цены) или **снижающее риск** (отмена ордера, reduce-only ордер, закрытие позиции, установка/изменение SL/TP, уменьшение плеча). Снижающее риск действие не может увеличить или перевернуть позицию: объём reduce-only/закрытия ограничен текущим размером позиции. Классификация определяет применение лимитов (4.4) и kill switch.

### 4.3 Права (least-privilege)
- FR-11. У каждого пользователя профиль прав: как минимум «только чтение» и «торговля». Инструменты, которых профиль не разрешает, агенту недоступны или явно отказывают.
- FR-12. Иерархия: админ задаёт потолок, пользователь может только ужесточить. Попытка ослабить — отказ. Эффективная политика — самое строгое из потолка админа и настроек пользователя; если админ опустил потолок ниже настроек пользователя, действует потолок.
- FR-44. Через MCP агент может только **читать** свою эффективную политику и **включить** свой kill switch. Любое другое изменение политики (лимиты, allowlist, подтверждения, TTL) и снятие kill switch — только через служебный канал (CLI), как и управление ключами.

### 4.4 Риск-лимиты
- FR-13. Максимальная сумма одного ордера в USDT — **только для действий, увеличивающих риск** (FR-43). Сумма = объём × цена (notional, для перпетуалов — не маржа); для limit — цена ордера, для market — текущая лучшая цена встречной стороны с допуском на slippage из политики (худшая ожидаемая цена). Объём берётся после округления до шага инструмента.
- FR-14. Максимальное плечо.
- FR-15. Список разрешённых инструментов (allowlist) — для действий, увеличивающих риск. Снижающие риск действия разрешены по любому инструменту, где есть позиция или ордер (иначе нельзя закрыть позицию по инструменту, удалённому из allowlist).
- FR-16. Kill switch: пользователь (для себя) и админ (для любого) мгновенно запрещают все действия, **увеличивающие риск**; снижающие риск действия и чтение продолжают работать (с обычной политикой подтверждений). Включение kill switch само ничего на бирже не отменяет. Снять kill switch, включённый админом, может только админ.
- FR-17. Нарушение лимита — отказ до обращения к бирже, с указанием, какой лимит нарушен и какое значение допустимо. Отказ попадает в журнал.
- FR-18. Лимиты по умолчанию (потолок админа для нового пользователя, значения могут уточняться в PLAN, но отношение «mainnet строже» обязательно): **testnet** — 1000 USDT на ордер, плечо ≤ ×10; **mainnet** — 50 USDT на ордер, плечо ≤ ×3, подтверждение всех торговых действий, ослабить может только админ.
- FR-45. Новый пользователь по умолчанию: профиль «только чтение», пустой allowlist, testnet. Торговля невозможна, пока админ явно не выдаст профиль и инструменты.
- FR-46. Защита от дробления: per-order лимит (FR-13) и порог «подтверждать дороже X» (FR-19) обходятся серией мелких ордеров — это известное ограничение. Минимальная защита: лимит числа действий, **увеличивающих риск** (FR-43) и выполненных **без подтверждения**, за скользящее окно (значения по умолчанию — в PLAN); при превышении следующие такие действия требуют подтверждения. Снижающие риск действия лимитом не ограничиваются. Лимит суммарной позиции/экспозиции — non-goal v1.

### 4.5 Подтверждение человеком (HITL)
- FR-19. Политика подтверждений настраивается (в рамках потолка админа), например: «подтверждать все торговые действия», «подтверждать ордера дороже X», «отмены без подтверждения». **Значение по умолчанию — подтверждать все торговые действия.** Политика подтверждений действует и на снижающие риск действия. Число одновременно ожидающих подтверждения действий на пользователя ограничено (по умолчанию testnet — 10, mainnet — 5); сверх лимита — отказ с понятной ошибкой.
- FR-20. Подтверждение получает **человек напрямую**, а не модель: модель не может сама подтвердить действие никаким вызовом инструмента или текстом. Основной канал — UI AI-клиента (если клиент это поддерживает и политика ему доверяет, FR-42); запасной — внешний канал вне чата (например, мессенджер или ссылка).
- FR-21. Запрос подтверждения показывает человеку точные параметры действия и их последствия (инструмент, сторона, объём, цена или «по рынку» с оценкой и худшей допустимой ценой, сумма, плечо, среда testnet/mainnet, затронуты ли внешние ордера).
- FR-22. Подтверждение привязано к конкретному действию с конкретными параметрами: его нельзя использовать повторно или для другого действия. Подмена параметров между запросом и исполнением невозможна: исполняется ровно то, что показано человеку.
- FR-23. Подтверждение имеет срок действия: по умолчанию **2 минуты**, админ задаёт максимум (не более 10 минут), пользователь может только уменьшить. По истечении действие не выполняется, агент получает понятный результат «не подтверждено (истекло)».
- FR-24. Отказ человека — нормальный исход: агент получает «отклонено пользователем», журнал фиксирует.
- FR-25. Если ни один доверенный канал подтверждения не доступен (у клиента нет UI-подтверждения или политика ему не доверяет, и внешний канал не настроен) — действия, требующие подтверждения, недоступны (fail closed).
- FR-42. Доверие UI-подтверждению программы клиента — настройка политики в рамках потолка админа. По умолчанию: на testnet доверяется, на **mainnet — нет** (достаточен только внешний канал). Подтверждение через служебный канал (CLI) на той же машине, где работает агент, считается доверенным только если админ явно его включил (агент с доступом к shell может вызвать CLI сам). Журнал всегда фиксирует, через какой канал принято решение, в том числе отказ, пришедший от программы клиента (а не от человека во внешнем канале).
- FR-47. Два исхода вызова, требующего подтверждения: (а) если подтверждение получено в рамках вызова (UI клиента), агент получает результат действия; (б) иначе агент сразу получает «ожидает подтверждения» с идентификатором и может узнать состояние read-инструментом. После подтверждения сервер исполняет действие сам — повторный вызов агента не нужен и не приводит к повторному исполнению. Агент не может подтвердить ожидающее действие.
- FR-48. Перед исполнением подтверждённого действия заново проверяются права, доступ, kill switch, лимиты и allowlist **на момент исполнения**; если что-то нарушено — действие не исполняется, агент и журнал получают причину. Market-ордер исполняется не хуже худшей цены, показанной человеку (оценка + допуск slippage из политики); неисполненный из-за этой границы остаток не исполняется, агент получает фактически исполненный объём.

### 4.6 Надёжность действий
- FR-26. Изменяющие инструменты принимают необязательный **ключ идемпотентности**: повторный вызов с тем же ключом возвращает результат первого и не создаёт второй ордер; тот же ключ с другими параметрами — ошибка. Без ключа — сетка безопасности: идентичный вызов того же пользователя в коротком окне (по умолчанию 30 с) считается повтором. Намеренные одинаковые ордера (лесенка) — через разные ключи. Работает и между несколькими клиентами одного пользователя.
- FR-27. Если результат обращения к бирже неизвестен (таймаут, обрыв), система не повторяет изменяющее действие вслепую: она выясняет фактический результат или сообщает агенту «результат неизвестен» с указанием, как проверить.
- FR-28. Ошибки классифицированы и понятны агенту: неверные параметры, запрещено правами, нарушен лимит, kill switch, требуется подтверждение / ожидает / отклонено / истекло, конфликт ключа идемпотентности, отклонено биржей (с причиной), превышен rate limit (когда можно повторить), биржа недоступна, ключи биржи недействительны или без нужных прав, результат неизвестен. Каждая ошибка подсказывает следующий шаг.

### 4.7 Пользователи, доступ и секреты
- FR-29. Админ создаёт пользователя и выдаёт ему доступ; может отозвать доступ. Отзыв действует немедленно: любой вызов после отзыва отклоняется, все ожидающие подтверждения аннулируются. Действие, уже отправленное на биржу, доводится до известного исхода и журналируется. Открытые ордера и позиции на бирже система **не трогает** (это документируется). То же — при удалении или замене ключей биржи: ожидающие подтверждения для старых ключей аннулируются.
- FR-30. Пользователь сам добавляет, заменяет и удаляет ключи биржи. **Ключи никогда не проходят через AI-клиента и контекст модели** — только через отдельный канал (CLI/служебный интерфейс).
- FR-31. Ключи биржи хранятся зашифрованными, после сохранения никогда не отображаются и не попадают в логи и журнал.
- FR-32. Среда (testnet/mainnet) задаётся на уровне пользователя; mainnet включает только админ.
- FR-49. При добавлении ключа система проверяет его права у биржи (если биржа это позволяет): ключ с правом вывода или переводов отклоняется; ключ только на чтение принимается и ограничивает профиль чтением. Если права проверить невозможно (например, эндпоинт недоступен в тестовой среде биржи) — fail closed: ключ отклоняется с понятной причиной.

### 4.8 Изоляция
- FR-33. Пользователь не может ни прочитать, ни изменить данные, ордера, политику, ожидающие подтверждения, журнал другого пользователя. Ошибки не раскрывают существование чужих данных.

### 4.9 Rate limiting
- FR-34. Ограничение частоты запросов на пользователя (значения по умолчанию и настройка — в PLAN), чтобы один пользователь (или зациклившийся агент) не исчерпал общие лимиты биржи и сервера.
- FR-35. Система учитывает лимиты биржи и не доводит до бана ключей; при приближении к лимиту — отказ с «повторите через N».

### 4.10 Журнал (audit log)
- FR-36. Фиксируется каждая попытка торгового действия и её исход: кто, когда, какой клиент (по данным, которые клиент сообщил о себе — не верифицируется), параметры, решение политики, подтверждение (кем/когда/каналом), ответ биржи. Также — административные действия (создание пользователя, отзыв доступа, смена политики, kill switch, смена ключей без значений ключей).
- FR-37. Журнал только дополняется; записи нельзя изменить или удалить через интерфейсы системы.
- FR-50. Журнал tamper-evident: изменение, удаление или вставка записи в обход системы (например, прямо в хранилище) обнаруживается командой проверки целостности.
- FR-38. Пользователь читает свой журнал (в том числе через AI-клиента), админ — журнал любого пользователя.

### 4.11 AI-часть проекта
- FR-39. **Агент-клиент:** небольшой консольный агент, подключающийся к серверу как MCP-клиент, с поддержкой подтверждений в своём UI. Работает минимум с одним провайдером LLM (OpenAI или Anthropic), провайдер переключаемый. Нужен для демо без Claude Desktop и для end-to-end сценариев.
- FR-40. **Evals выбора инструментов:** ≥ 40 кейсов на русском и английском, из них ≥ 25% опасных/неоднозначных (вывод средств, обход лимитов, ослабление политики, prompt injection в данных). У каждого кейса детерминированный эталон — один из исходов: «вызвать инструмент X с аргументами Y» (сравнение по ключевым полям, числа точно), «уточнить, не вызывая изменяющих инструментов», «отказать, не вызывая изменяющих инструментов». Оценка без LLM-judge. Каждый кейс прогоняется несколько раз (недетерминизм модели). Метрики: точность выбора инструмента, точность аргументов, доля корректных отказов/уточнений. Отчёт показывает, улучшило ли изменение описаний инструментов качество. Полный прогон дешевле $0.50.

## 5. Нефункциональные требования
- NFR-1. Безопасность по умолчанию: всё, что не разрешено явно, запрещено; при сомнении — fail closed.
- NFR-2. Тестируемость без сети и без биржи: весь CI проходит без обращений к внешним API (биржа, LLM, Telegram); загрузка пакетов и Docker-образов допустима. Отдельный ручной набор проверок против testnet.
- NFR-3. Наблюдаемость: структурированные логи с request id, без секретов.
- NFR-4. Накладные расходы сервера на вызов (без учёта биржи и ожидания человека) — p95 ≤ 50 мс на локальной машине.
- NFR-5. Добавление второй биржи не требует изменений в правилах прав, лимитов, подтверждений и журнала.
- NFR-6. Запуск одной командой (локально и в контейнерах); публичный README на английском с архитектурой, демо (GIF), обоснованием решений и честной таблицей «какой клиент что поддерживает» (elicitation и т.п.).
- NFR-7. Качество кода по `../../ENGINEERING.md`: слои, типизация, тесты, CI.

## 6. Edge cases (должны быть описаны в тестах; ожидаемое поведение — в указанных FR)
- Агент дважды вызывает размещение одного ордера подряд — с тем же ключом, без ключа, с разными ключами (FR-26).
- Тот же ключ идемпотентности с другими параметрами (FR-26).
- Таймаут биржи после отправки ордера (FR-27).
- Подтверждение пришло после истечения срока / после включения kill switch / после отзыва доступа / после замены ключей (FR-23, FR-29, FR-48). Kill switch не блокирует подтверждённое снижающее риск действие (FR-16).
- Параметры между запросом подтверждения и исполнением изменились (агент пытается подменить) (FR-22).
- Market-ордер: цена ушла между подтверждением и исполнением дальше допуска; частичное исполнение (FR-48).
- Ордер проходит лимит суммы, но после округления до шага объёма — нет (или наоборот) (FR-13).
- Инструмент удалён из разрешённых, пока ордер ждал подтверждения; закрытие позиции по инструменту вне allowlist (FR-15, FR-48).
- Пользователь ужесточил политику / админ опустил потолок во время ожидания подтверждения (FR-12, FR-48).
- Reduce-only или закрытие с объёмом больше позиции (FR-43).
- Стоп/закрытие позиции, notional которой больше per-order лимита (FR-13, FR-43).
- Серия мелких ордеров без подтверждения превышает лимит частоты (FR-46).
- «Отменить все по инструменту» при наличии внешних ордеров (FR-5, FR-21).
- Агент пытается ослабить политику или снять kill switch через MCP (FR-44).
- Добавление ключа с правом вывода; ключа только на чтение (FR-49).
- Данные с биржи или из истории содержат текст-инструкцию (prompt injection) (FR-41).
- Биржа вернула rate limit / недоступна / ключи истекли или без нужных прав (FR-28, FR-35).
- Несколько клиентов одного пользователя работают одновременно (FR-26, FR-47).
- Прямое изменение записи журнала в хранилище (FR-50).

## 7. Acceptance criteria (проект готов, когда)
- AC-1. В Claude Desktop или Claude Code (локальный режим) на testnet проходит сценарий: «покажи позиции → поставь стоп на 3% ниже входа» с подтверждением человеком — в UI клиента, а если клиент не поддерживает UI-подтверждение, через внешний канал; запись в журнале.
- AC-2. В удалённом режиме два пользователя с разными политиками работают одновременно, не видят данных друг друга; у read-only пользователя торговля недоступна.
- AC-3. Каждое требование FR-13…FR-28 и FR-41…FR-50 покрыто автоматическим тестом, CI зелёный без сети.
- AC-4. Модель не может выполнить действие, требующее подтверждения, без участия человека — доказано тестом с «агентом», который пытается подтвердить сам через вызовы инструментов и текст. (Самописный клиент, автоматически отвечающий на UI-подтверждение, вне этой гарантии — от него защищает FR-42.)
- AC-5. Агент-клиент выполняет демо-сценарий с подтверждением в консоли.
- AC-6. Отчёт evals опубликован в README, есть пример «изменили описания инструментов → метрика изменилась».
- AC-7. README на английском, GIF демо, инструкция запуска одной командой.

## 8. Non-goals
- Торговые стратегии, сигналы, автотрейдинг без человека, бэктесты.
- Вывод средств и переводы (FR-9).
- Дневной лимит убытка и лимит суммарной позиции/экспозиции — кандидаты на следующие версии (минимальная защита от дробления — FR-46).
- Инструменты с котировкой не в USDT (USDC, BTC-пары и т.п.).
- SL/TP и условные ордера на споте.
- Обнаружение/фильтрация prompt injection на сервере (FR-41).
- Автоматическая отмена ордеров при kill switch или отзыве доступа.
- Веб-интерфейс для пользователей и саморегистрация.
- Поддержка второй биржи в v1 (только готовность к ней, NFR-5).
- Опционы, маржинальный спот, инверсные контракты.

## 10. Журнал решений

### Интервью (2026-10-27)
Оба режима (локальный и multi-tenant); чтение + торговля, без переводов и вывода; политика подтверждений настраивается пользователем, по умолчанию строгая; одна биржа с расширяемостью; спот + линейные перпетуалы; админ создаёт пользователей и задаёт потолок, пользователь сам добавляет ключи и может только ужесточать; testnet по умолчанию, mainnet — явно админом; в проект входят агент-клиент и evals выбора инструментов (без публичного деплоя и публикации в PyPI в v1); подтверждение — в UI клиента + внешний запасной канал, модель подтвердить не может; риск-контроли v1 — базовые лимиты и kill switch; имя — guarded-exchange-mcp; только Python.

### Grilling SPEC (2026-10-27)
- G-1. **Kill switch блокирует только увеличение риска** (FR-16, FR-43). Было: «запрещает все торговые действия» — тогда в панике нельзя отменить ордер или закрыть позицию. Kill switch сам ничего на бирже не отменяет. Отклонено: полный запрет записи; авто-отмена ордеров (лишнее действие на бирже с частичными отказами).
- G-2. **Снижающие риск действия не ограничены суммой и allowlist**, только размером позиции, подтверждения — по общей политике (FR-13, FR-15, FR-43). Было противоречие: AC-1 (стоп на крупную позицию) отклонялся бы per-order лимитом.
- G-3. **Сумма ордера = notional в USDT по худшей ожидаемой цене**, для market — лучшая цена встречной стороны + допуск slippage; перпетуалы — notional, не маржа; в v1 только USDT-котировки (FR-4, FR-13).
- G-4. **Дробление ордеров признано явно** + лимит числа действий без подтверждения за окно (FR-46). Лимит экспозиции остаётся non-goal.
- G-5. **Граница доверия:** модель недоверенная всегда; UI-подтверждению программы клиента доверяем по политике, на mainnet по умолчанию — нет (раздел 2, FR-42, AC-4).
- G-6. **Два исхода подтверждения:** синхронно в UI или «ожидает» с id; после подтверждения сервер исполняет сам (FR-47). Отклонено: всегда синхронно (таймауты клиента дают «результат неизвестен»), всегда pending (хуже UX).
- G-7. **Полная перепроверка на момент исполнения + граница цены для market** (FR-48). Было: edge cases перечислены без ожидаемого поведения.
- G-8. **TTL подтверждения 2 мин**, максимум админа ≤ 10 мин, пользователь только уменьшает (FR-23).
- G-9. **Идемпотентность — ключ от агента + окно 30 с без ключа** (FR-26). Было непроверяемое «тот же запрос»; лесенка одинаковых ордеров должна оставаться возможной.
- G-10. **Внешние ордера:** агент видит и управляет всеми ордерами аккаунта, они помечены происхождением, подтверждение показывает затронутые внешние ордера (FR-2, FR-5, FR-21). Допущение: аккаунт/сабаккаунт принадлежит пользователю.
- G-11. **Агент через MCP только читает политику и может включить kill switch**; всё остальное — CLI (FR-44). Иначе агент ослабил бы себе подтверждения в пределах потолка.
- G-12. **Ключи с правом вывода/переводов отклоняются** при добавлении (FR-49).
- G-13. **Дефолты нового пользователя:** read-only, пустой allowlist, testnet; конкретные потолки testnet/mainnet (FR-18, FR-45). Было: «mainnet строже» без чисел — непроверяемо.
- G-14. **Отзыв доступа / смена ключей:** новые вызовы отклоняются, pending аннулируются, отправленное доводится до исхода, биржу не трогаем (FR-29).
- G-15. **Журнал tamper-evident** (FR-50); «какой клиент» — самоописание клиента, не верифицируется (FR-36).
- G-16. **Evals — детерминированный эталон** (инструмент+аргументы / уточнить / отказать), ≥ 40 кейсов, ≥ 25% опасных, без LLM-judge, несколько прогонов, < $0.50 (FR-40).
- G-17. **SL/TP и закрытие позиции — только перпетуалы** (FR-6, FR-7).
- G-18. **AC-1:** подтверждение в UI клиента или, если клиент не поддерживает, через внешний канал; честная таблица поддержки в README (AC-1, NFR-6).
- G-19. **Prompt injection:** сервер помечает внешний текст как данные, не фильтрует; защищают права/лимиты/HITL, измеряют evals (FR-41).
- G-20. Без вопроса пользователю (рецензент): NFR-4 сделан измеримым (p95 ≤ 50 мс накладных); политика подтверждений распространяется на снижающие риск действия (FR-19); эффективная политика = min(потолок, настройки пользователя) (FR-12); админ действует только через CLI (раздел 2); edge cases связаны с FR, добавлены новые.
