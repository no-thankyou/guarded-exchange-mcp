# 010: История ордеров и сделок
Статус: DONE
Зависит от: 008
Требования: FR-2, FR-3, FR-41

## Цель
Агент читает историю ордеров и сделок за период с пагинацией, с пометкой происхождения.

## Scope
- MCP: `get_order_history`, `get_trades` (`/v5/order/history`, `/v5/execution/list`), период, курсор, лимиты Bybit на глубину истории — в описании инструмента.
- Происхождение — по журналу и префиксу `gx-`.

## Non-scope
- Журнал через MCP (025).

### Лимиты Bybit (проверено по официальной документации V5, 2026-11-03)
- [Get Order History](https://bybit-exchange.github.io/docs/v5/order/order-list): `startTime`/`endTime` в мс; без обоих — последние 7 дней; только `startTime` — `[startTime, startTime + 7 дней]`; только `endTime` — `[endTime − 7 дней, endTime]`; оба — `endTime − startTime ≤ 7 дней`. `limit` 1–50 (по умолчанию 20), `cursor` = `nextPageCursor` предыдущего ответа. Хранение: за последние 7 дней — все закрытые статусы, кроме `Cancelled`, `Rejected`, `Deactivated`; эти три — только за последние 24 часа; старше 7 дней — только ордера с исполнениями (`Filled`, `PartiallyFilledCanceled`). Глубина — «2 years» в навигации сайта; в исходнике документации ([order-list.mdx](https://github.com/bybit-exchange/docs/blob/main/docs/v5/order/order-list.mdx)) — «Unified account … supports getting the past 730 days historical data». Параметры `symbol`/`baseCoin`/`settleCoin` есть.
- [Get Trade History](https://bybit-exchange.github.io/docs/v5/order/execution) (`/v5/execution/list`): те же правила периода (7 дней), `limit` 1–100 (по умолчанию 50), `cursor`; глубина — 730 дней для UTA ([execution.mdx](https://github.com/bybit-exchange/docs/blob/main/docs/v5/order/execution.mdx)), «2 years» в навигации. Есть `settleCoin`.
- [Enums](https://bybit-exchange.github.io/docs/v5/enum): `orderStatus` открытые — `New`, `PartiallyFilled`, `Untriggered`; закрытые — `Rejected`, `PartiallyFilledCanceled`, `Filled`, `Cancelled`, `Triggered`, `Deactivated`. `execType`: `Trade`, `AdlTrade`, `Funding`, `BustTrade`, `Delivery`, `Settle`, `BlockTrade`, `MovePosition`, `FutureSpread`, … `rejectReason` — enum `EC_*` (`EC_NoError` = нет причины).
- «500 закрытых» из постановки — это лимит `order/realtime` (не более 500 последних закрытых ордеров на категорию, `docs/research/exchange.md`), а не `order/history`; у истории ограничение по отменённым — 24 часа. В описание инструмента и README вошли правила `order/history`.
- Отправка курсора: официальный SDK [pybit](https://github.com/bybit-exchange/pybit/blob/master/pybit/_http_manager.py) (`prepare_payload`) собирает GET-query как `key=value` без URL-кодирования — курсор (Bybit отдаёт его уже percent-encoded, например `page_args%3D…%26symbol%3D6%26`, `132766%3A2%2C132766%3A2`) уходит как есть, подпись — по этой строке. На живой бирже не проверялось (CI без сети): см. «Как проверить руками».

### Итоги реализации (2026-11-03, исполнитель)
- **Порт `AccountHistoryReader`** (`application/ports.py`) — отдельный от `AccountReader`: `get_order_history(keys, category, *, symbol, period, exchange_cursor, limit)` и `get_trades(...)` → `HistoryPage[T](items, next_exchange_cursor, omitted)`. Отдельный порт, чтобы не трогать `FakeAccount` и не менять контракт чтения аккаунта (у истории курсор и период, у открытых ордеров — `limit + 1`). Реализует тот же `BybitClient`. Фейк — `tests/fakes_history.py` (отдельно от `tests/fakes.py`, чтобы не конфликтовать с 011).
- **Домен `domain/history.py`:** `HistoryPeriod` (UTC, aware, `start < end`, ≤ 7 дней), `history_period(start, end, now)` — правила Bybit (см. выше) с нашими уточнениями: время без смещения = UTC, границы усекаются до целых мс, конец в будущем обрезается до `now` (в будущем ничего нет; агент видит реальный период в `period_start`/`period_end`), начало не раньше `now − 730 дней`. Ошибки — `InvalidParams` c `details={field, reason: "period"}` и `next_step`: для окна > 7 дней — «Split the period… e.g. start_time=X end_time=X+7d» (готовое валидное окно), для глубины — самая ранняя допустимая дата, для пустого/перевёрнутого/будущего — что поправить. `ExecutionKind` (`trade`, `liquidation` ← `BustTrade`, `auto_deleverage` ← `AdlTrade`, `funding`, `settlement` ← `Delivery`/`Settle`, `block_trade`, `other`), `Trade` (Decimal, UTC, `origin`, `client_order_id: UntrustedText`).
- **`OrderStatus`** расширен финальными статусами: `filled`, `cancelled`, `partially_filled_cancelled`, `rejected`, `triggered`, `deactivated` (раньше всё неоткрытое → `unknown`). Это видно и в `get_open_orders`: если `order/realtime` вернёт закрытый ордер, он придёт с настоящим статусом (тест `test_statuses_and_kinds_this_version_does_not_know_are_unknown_not_exchange_text` теперь проверяет `unknown` на действительно неизвестном статусе). `Order.reject_reason: UntrustedText | None = None` (по умолчанию — чтобы не трогать конструкторы 011); `OrderOut` получил `updated_at` (когда ордер закрылся) и `untrusted_text.reject_reason`.
- **Наш курсор** (`encode_cursor`/`decode_cursor`): URL-safe base64 от JSON `{v, k: orders|trades, c, s, a: start_ms, b: end_ms, t: курсор биржи}`. Зачем: Bybit требует тот же запрос с курсором, а «последние 7 дней» к следующему вызову сдвигаются — с нашим курсором вторая страница читается ровно с периодом и символом первой (`test_the_next_page_is_read_with_the_first_pages_period_and_symbol` двигает часы между вызовами). С курсором агент передаёт только `category` (должна совпасть) и `limit`; `symbol`/`start_time`/`end_time` вместе с курсором → `invalid_params` (`cursor_with_filters`); чужой/изменённый курсор, курсор другого инструмента → `invalid_cursor`. Курсор не подписан (HMAC): подделка даёт агенту только то, что он и так может запросить аргументами; всё внутри перепроверяется (период ≤ 7 дней, глубина на текущий момент, категория, символ по шаблону, длина).
- **Курсор биржи и инъекции.** На запрос: `wire_exchange_cursor` пропускает только `[A-Za-z0-9_.~-]` и `%XX`, до 512 символов, иначе `InvalidParams` до сети; подписанный query собирается `urlencode(..., safe="%")` — `%` не перекодируется (иначе `%3D` → `%253D`), всё остальное кодируется как раньше; сырых `&`, `=`, `#`, `?`, пробела в курсоре быть не может, значит, лишний параметр не подставить. Из ответа: курсор с символами вне алфавита percent-кодируется (биржа декодирует query один раз и получит то же значение), битый `%` → `exchange_unavailable`. Подпись покрывает ровно отправленную строку (`_assert_signed` в тестах).
- **Конец страниц.** Bybit присылает `nextPageCursor` и на последней странице, поэтому страница короче `limit` — последняя (`next_cursor` нет); полная страница с курсором → `has_more: true`, следующая может оказаться пустой (так и сказано в описании `next_cursor`). `limit` 1–50 (по умолчанию 20) для обоих инструментов (`account_items_limit`, FR-3). Ответ не режется в use case (в отличие от 008): курсор указывает за последнюю строку биржи, обрезка потеряла бы строки; адаптер отказывает, если биржа вернула больше `limit`.
- **Запросы:** обе границы периода отправляются всегда (`startTime`/`endTime`, точные мс без float); linear без символа — `settleCoin=USDT` (как в 008), spot — без. Ошибки — как у чтения аккаунта (`rate_limited` с `retry_after_s`, `exchange_credentials_invalid`, `exchange_unavailable`).
- **FR-41:** свободный текст — `orderLinkId` (и у ордеров, и у исполнений) и `rejectReason` (кроме `EC_NoError`; в документации это enum, но значения приходят с биржи и не сверяются с нашим списком) — только в `untrusted_text`, обрезка до 64 символов. `feeCurrency` — только если это код монеты по шаблону, иначе поле отсутствует; `execId`/`orderId` — шаблон идентификатора, иначе `exchange_unavailable`. Unit-тест обходит JSON обоих ответов и сверяет каждую строку вне `untrusted_text` с правилом поля (как в 008).
- **`omitted`:** строки, которые v1 не показывает — датированные фьючерсы, ордера hedge mode (в истории это не отказ всего чтения, в отличие от открытых ордеров: прошлые ордера в hedge mode не должны делать историю нечитаемой), исполнения с неизвестной стороной.
- **Происхождение:** `origin` — по префиксу `gx-` (`order_origin`, как в 008); у сделки — по `orderLinkId` исполненного ордера. **Сверки с журналом нет** — она вне scope до 012 (в журнале появятся записи об отправленных ордерах и ответ на вопрос «наш ли это id»), сказано в описаниях полей и README.
- **MCP:** `get_order_history`, `get_trades` (`interface/mcp/tools/history.py`, read-only, `Permission.READ`), аргументы `category` (обязателен), `symbol`, `start_time`, `end_time` (ISO 8601, `datetime` в схеме), `cursor` (1–1024), `limit`; правила периода, хранение отменённых 24 ч и курсор — в описании инструмента. Ответ: `category`, `period_start`, `period_end`, `orders`/`trades`, `has_more`, `next_cursor` (нет на последней странице), `omitted`.
- Миграций нет. Фикстуры `tests/fixtures/bybit/history/*.json` построены офлайн по документации (поле `_source`), на биржу не ходили.
- **Слияние с 011** (идёт параллельно): правки в общих файлах локальны — `mapper.py` (статусы, поле `rejectReason`, секция истории между `open_orders_from_result` и `_order`; конец файла не тронут), `domain/account.py` (только `OrderStatus` и поле `Order.reject_reason` со значением по умолчанию), `client.py` (методы после `get_open_orders`, `_query` вместо `urlencode`), `server.py`/`access.py`/`bootstrap.py`/`tests/e2e/support.py` (по 2–3 строки). Ожидаемые тривиальные конфликты: импорты в `client.py`/`schemas.py`/`server.py`, список полей `UseCases`. `tests/fakes.py` не тронут. README: строка «Status» и раздел Architecture не обновлены (их меняет 011) — после слияния добавить туда `get_order_history`, `get_trades` и `GetOrderHistory / GetTrades -> ReadCredential, AccountHistoryReader`.

Как проверить руками: `uv run pytest tests/e2e/test_mcp_history_reads.py tests/integration/test_bybit_history_reads.py -v`. На testnet (не CI): `uv run guarded-exchange keys add`, затем в Claude Code — «покажи историю ордеров на linear за последние 3 дня», «сделки по spot за неделю», «история за месяц» (ответ `invalid_params` с подсказкой разбить по 7 дней); при `has_more` — «следующая страница» (агент передаёт `cursor`). Главное, что стоит проверить на живой бирже, — вторая страница с курсором (verbatim, без перекодирования) действительно продолжает первую; если биржа ответит ошибкой подписи или повтором первой страницы — поменять `safe="%"` на обычное кодирование в `client._query` (одна строка) и тест `test_the_next_page_sends_the_exchange_cursor_verbatim_and_signs_it`.

### Предложения (вне scope)
- Сверка `origin` с журналом отправленных ордеров (012): `system` только если `orderLinkId` есть в журнале пользователя, иначе `external` даже с префиксом `gx-`.
- `cancelType` (`CancelByUser`, `CancelByReduceOnly`, `CancelByPrepareLiq`, …) как наш enum `cancelled_by` — агенту полезно отличать отмену пользователем от ликвидации; сейчас не выводится.
- Фильтр `execType` в `get_trades` (только `trade`), фильтр `orderStatus` в `get_order_history` — по результатам evals.
- Подписанный (HMAC) курсор, если появятся данные в курсоре, которые агент не должен менять; сейчас не нужен.
- `limit` до 100 для `get_trades` (максимум Bybit) — если evals покажут, что 50 мало.
- Ручной прогон на testnet с записью фикстур `order/history` и `execution/list` (заменить офлайн-фикстуры записанными, как в спайке 004).
