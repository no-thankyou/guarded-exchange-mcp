# 012: Идемпотентность и неизвестный исход
Статус: IN_REVIEW
Зависит от: 011
Требования: FR-26, FR-27, FR-28

## Цель
Повтор изменяющего вызова не создаёт второй ордер (ключ агента или окно 30 с без ключа), между клиентами одного пользователя; неизвестный исход разведывается, а не повторяется вслепую.

## Scope
- `idempotency_records` (ADR-014, D-20): явный ключ (TTL 24 ч) — `INSERT … ON CONFLICT DO NOTHING RETURNING`; без ключа — fingerprint только для действий, увеличивающих риск; canonical args (Decimal нормализованы, float запрещён).
- Проверка повтора до rate limit; тот же ключ + другие параметры → `idempotency_conflict`; запись обновляется финальным исходом.
- FR-27: таймаут/обрыв после отправки → `GET order/realtime?orderLinkId` → `order/history`; не найден → `outcome_unknown` с подсказкой (не FAILED); никаких автоматических повторов POST.
- Описание инструментов: «новая попытка — новый ключ».

## Non-scope
- Pending и идемпотентность (016), действия без client id (014).

## Заметки
- Из ревью 011: если после принятого биржей ордера не удалось записать `order_outcome` (например, `database is locked`), агент получает «accepted, filled unknown», а журнал содержит только `order_attempt`. Повтор вызова агентом в этом случае создаст второй ордер с новым `action_id`; защита — ключ идемпотентности / окно 30 с (D-20), а восстановление недостающего `order_outcome` — разведка по `client_order_id` из `order_attempt`.
  - **Решено частично (2026-11-03).** `order_outcome` и финальный ответ в записи идемпотентности пишутся одной транзакцией; если она не прошла, запись остаётся `sent`, и повтор (тот же ключ или тот же вызов без ключа) получает `outcome_unknown`/`in_progress`, а не второй ордер — `test_a_journal_failure_after_an_accepted_order_leaves_the_key_claimed`. Восстановление недостающего `order_outcome` разведкой **не сделано**: это восстановление после сбоя/рестарта без вызова агента, его естественное место — executor 016 (ADR-006: `EXECUTING` → разведка по `client_order_id` при старте), см. «Предложения». Делать его в повторе агента — значит звать биржу из ответа повтору (D-20 (1) против) и гадать, жив ли ещё первый вызов.
- Из ревью 011 (раунд 2), предложение: нераспознанный `retCode` на изменяющем POST (`order/create`, позже `amend`/`cancel`) сейчас — определённый отказ (`exchange_rejected`), неизвестными считаются только коды из явного списка `UNKNOWN_OUTCOME_RET_CODES`. Рассмотреть «unknown по умолчанию» для изменяющих POST (определённые отказы — явным списком), раз разведка по `orderLinkId` здесь появится.
  - **Сделано.** `error_for_create`: определённый отказ — только документированные семейства (`10001–10029`, `110001–110999`, `170001–170999`, `3400001–3401010`) минус явный список неизвестных; всё прочее → `outcome_unknown` (`reason=unrecognised_exchange_code`) и разведка. Добавлен `10014` «Invalid duplicate request» в неизвестные (документация 2026-11-03). Тест `test_an_unrecognised_create_code_is_unknown_and_documented_refusals_stay_definite`. Семейства, а не поштучный список отказов: поштучный список отказов (сотни кодов) устаревал бы так же, как список неизвестных; цена — незнакомый код отказа даёт «неизвестно» вместо «отклонено» (безопасная сторона). Для `amend`/`cancel` — в 013 тем же способом.
- Из ревью 011 (раунд 2): общий дедлайн POST под shield. `read_timeout` httpx ограничивает только простой между чанками ответа, а не всё время запроса; медленно капающий ответ может держать shield (и вызов агента) долго. Добавить общий дедлайн (`anyio.fail_after` вокруг отправки внутри shield) → по истечении `outcome_unknown` и разведка.
  - **Сделано.** `anyio.fail_after(GX_ORDER_SEND_DEADLINE_S, 15 с)` вокруг `place_order` внутри shield в application (гарантия use case для любого адаптера) → `outcome_unknown` (`reason=send_deadline`) → разведка, сама ограниченная `move_on_after` 15 с. Тесты `test_a_send_that_never_answers_hits_the_overall_deadline_and_is_looked_up`, `test_a_lookup_that_never_answers_is_bounded`.
- Из ревью 011 (раунд 3, minor): отказ без лучшей цены (`_best` в `domain/orders.py` → `ExchangeUnavailable(reason=no_market_price)` в раннем `_plan` после `_read_market`) не журналируется как `order_refused` (`stage: pre_check`), вопреки PLAN «Тикет 011» (5). Ловить его так же, как ошибки `_read_market`.
  - **Сделано.** Ранний план — внутри того же блока, что проверка ключа и чтения биржи (`_prepare`): ошибки ввода не журналируются, остальные — `order_refused`/`pre_check`. Тест `test_a_market_order_without_a_best_price_is_journaled_as_a_refusal`.
- Из ревью 011 (раунд 3, minor): сбой записи раннего отказа (`order_refused`, `stage: pre_check`) подменяет исходную ошибку на `internal_error`. Ордер не отправлен, так что безопасно; для единообразия — try/log, как `_try_journal_outcome`.
  - **Сделано.** `_journal_early_refusal` ловит сбой записи и пишет в лог `order_refused_not_recorded`; агент получает исходную ошибку. Тест `test_a_journal_failure_of_an_early_refusal_keeps_the_original_error`.

### Итоги реализации (2026-11-03)
- **Один путь.** Всё внутри `application/submit_action.py::SubmitPlaceOrder`: разбор → principal → профиль/среда → **захват записи идемпотентности** → ключ (D-24) → чтения биржи → ранний план → решение (fencing + `order_attempt` + `sent` в одной транзакции под `lock_user`) → отправка под shield с общим дедлайном → при неизвестном исходе разведка → `order_outcome` + ответ в запись одной транзакцией. Ответ повтору — только из БД, без вызовов биржи (D-20 (1)). Подробные решения — PLAN, ADR-014 «Тикет 012» (пункты 1–11).
- **Хранение:** таблица `idempotency_records` (миграция 0007), `pk(user_id, key_kind, key)` (`unique(action_id)` снят в ревью 1), CHECK «ответ есть ⇔ статус `unknown`/`completed`», индекс `(user_id, expires_at)`. Захват — одна команда `INSERT … ON CONFLICT DO UPDATE … WHERE expires_at <= now RETURNING` для обоих видов ключа (отличие от «DO NOTHING» в тикете: иначе явный ключ не освобождался бы через 24 ч). Изменения записи условны по `action_id` держателя (fencing).
- **Fencing против двойной отправки при истёкшем fingerprint.** Без него вызов, застрявший перед решением дольше окна, и новый идентичный вызов отправили бы два ордера. Транзакция решения делает `mark_sent` только у держателя; не держатель → ничего не отправляет (`outcome_unknown`, `reason=superseded`). Пока вызов в полёте, запись живёт ≥ 10 мин (`IN_FLIGHT_GUARD`); окно 30 с отсчитывается от ответа. Тест `test_a_stale_call_whose_claim_was_taken_over_sends_nothing`.
- **Какие ответы хранятся** (`domain.idempotency.keeps_record`): ордер есть или может быть — всегда; определённый отказ — только для явного ключа (D-20 (5)); переходящие сбои и всё до решения (в т.ч. отмена вызова) освобождают ключ, чтобы «повторите через несколько секунд» работало с тем же ключом. Тесты `test_a_refusal_with_a_key_is_answered_again_and_a_new_key_is_a_new_attempt`, `test_a_refusal_without_a_key_does_not_block_the_same_call_later`, `test_a_transient_failure_releases_the_key_so_the_retry_runs`, `test_a_definite_exchange_failure_after_sending_releases_or_keeps_by_kind`, `test_a_call_cancelled_before_its_decision_releases_its_key`, `test_an_unknown_outcome_is_kept_and_a_repeat_never_sends_again`, `test_a_repeat_during_the_first_call_is_in_progress_and_sends_nothing`.
- **Хэш вызова** — SHA-256 канонического `{tool, environment, args}` (`canonical_json`: Decimal нормализованы, float — ошибка). `credential_id` в хэш не входит: повтор после замены ключа должен получить ответ первого вызова. Вызов с явным ключом тоже захватывает fingerprint, если тот свободен (ревью 1); консультируют его только вызовы без ключа, поэтому лесенка одинаковых ордеров — разные ключи — работает.
- **MCP:** `place_order` принимает `idempotency_key` (pattern `IDEMPOTENCY_KEY_PATTERN`), описание — «новая попытка — новый ключ», повтор после таймаута — тем же ключом. Ответ: `result_source` (`placed`/`reconnaissance`/`replay`) и `next_step` для повтора/разведки; новый код ошибки `idempotency_conflict` (ADR-013, FR-28). Повторённая ошибка помечена `details.replayed=true`. Тесты `test_the_tool_offers_an_idempotency_key_and_says_a_new_attempt_needs_a_new_key`, `test_a_repeated_call_is_answered_as_a_replay_and_other_arguments_conflict`.
- **Изоляция (FR-33):** записи разных пользователей с одним ключом независимы — `test_the_same_key_of_two_users_is_two_records`.
- **Фейки:** `InMemoryDatabase` теперь сериализует write-транзакции (`anyio.Lock`, как `BEGIN IMMEDIATE`), иначе конкурентные тесты на фейках теряли бы обновления (показано тестом `test_the_fake_database_serialises_writers[without_lock]`, ревью 1); `InMemoryIdempotencyRepository` повторяет семантику SQL; `FakeTrading.find_order`, `history`, `hold_band`/`hold_find`.
- **Проверка тестов мутациями.** Каждый новый тест проверен временной мутацией кода (скрипт применял замену, гонял тест, возвращал файл); все мутации пойманы:

  - хэш без нормализации Decimal (`json.dumps(default=str)`) → оба теста «0.10»/«0.1», тест float;
  - без освобождения до решения → `test_a_transient_failure_…`, `test_a_call_cancelled_…`, `test_a_market_order_without_a_best_price_…`;

### Предложения (вне scope)
- **016:** восстановление при старте: записи `sent` старше `IN_FLIGHT_GUARD` и `order_attempt` без `order_outcome` → разведка по `client_order_id` и дописывание `order_outcome` (сейчас такая запись отвечает повтору `in_progress` до истечения: 24 ч для явного ключа, 10 мин от захвата для fingerprint). Тот же механизм нужен executor'у для `EXECUTING` (ADR-006).
- **016:** связать запись идемпотентности с pending (D-20 (2), (5)): повтор с тем же ключом во время ожидания подтверждения → тот же pending id; `REJECTED/EXPIRED` — сохранённый ответ.
- **013:** `error_for_amend`/`error_for_cancel` по тому же правилу «неизвестно по умолчанию вне документированных семейств»; разведка для них — по `orderId` (D-21).
- Повтор `outcome_unknown` с тем же ключом мог бы переразведывать (биржа догоняет за секунды), но это вызов биржи из ответа повтору — против D-20 (1); если понадобится, отдельным read-инструментом `get_order_status(client_order_id)`.
- Чтение истории по `orderLinkId` вне 7-дневного окна по умолчанию (`startTime` от `order_attempt.ts`) — для восстановления спустя дни.

### Ревью, раунд 1 (CHANGES_REQUESTED, исправлено 2026-11-03)
Каждый новый тест проверен временной мутацией (скрипт: замена в коде → прогон теста → возврат файла); все 26 мутаций пойманы.
1. **BLOCKER, коды «в обработке».** Spot `170035` «Submitted to the system for processing!» и `170149` «Create order failed» — в `UNKNOWN_OUTCOME_RET_CODES`; страница ошибок Bybit V5 пересканирована 2026-11-03 по словам processing/submitted/failed/system/timeout/duplicate: для `order/create` добавлен ещё `110030` «Duplicate orderId» (как дубль `orderLinkId`); `110114`, `110134` («try again later», ордер не принят) — определённые отказы; коды amend/cancel (`170147`, `170150`, `170191`, `170212`, `170310`, `170311`, `110079`) записаны в заметки тикета 013. Строки в `test_an_unrecognised_create_code_is_unknown_and_documented_refusals_stay_definite` (мутации: убрать 170035 / 170149 / 110030 — пойманы).
2. **Fencing по истечению.** `mark_sent(record, now)` требует `expires_at > now` и продлевает запись до `max(expires_at, now + IN_FLIGHT_GUARD)` одной командой; housekeeping удаляет только истёкшие отвеченные записи (`unknown`/`completed`), неотвеченные заменяет только перехват. SQL и фейк. Тесты: `test_a_claim_that_expired_during_the_reads_sends_nothing_and_the_next_call_sends_once` (истечение во время чтений → решение → идентичный вызов → ровно одна отправка), `test_sending_extends_the_claim_so_a_slow_send_is_not_taken_over`, `test_housekeeping_keeps_an_expired_unanswered_record`; SQL — `test_mark_sent_refuses_an_expired_claim_and_extends_a_live_one`, `test_housekeeping_never_deletes_an_unanswered_record`.
3. **Подсказка `outcome_unknown` по виду записи.** Явный ключ — «повторите с тем же ключом»; без ключа и reduce-only — «повтор позже поставит НОВЫЙ ордер, сначала проверьте по `client_order_id`». Fingerprint с неизвестным исходом живёт `IN_FLIGHT_GUARD` (10 мин). Описание инструмента исправлено. Тесты `test_an_unknown_outcome_warns_a_keyless_caller_that_a_later_repeat_is_a_new_order`, `test_a_keyless_unknown_outcome_is_kept_ten_minutes_not_thirty_seconds`.
4. **Баг при отправке** → `outcome_unknown` (`reason=internal_error`, `raise … from exc`, исключение в лог `order_send_failed`), запись `unknown`; повтор с ключом и без ключа ничего не отправляет — `test_a_bug_while_sending_is_outcome_unknown_and_repeats_send_nothing`; тест 011 `test_a_crash_while_sending_still_records_an_unknown_outcome` теперь ждёт `OutcomeUnknown`.
5. **Явные определённые коды до семейств:** ключ (`CREDENTIAL_RET_CODES`, в т.ч. `33004`) и лимит (`10006`, `10429` → `rate_limited`); `110030` — как дубль. Строки в том же табличном тесте.
6. **Чтение ордера после принятия** — `move_on_after(GX_ORDER_FILL_READ_DEADLINE_S, 5 с)` → `filled: unknown` — `test_a_read_back_that_never_answers_is_fill_unknown`.
7. **Устаревшие записи.** `sent` старше `IN_FLIGHT_GUARD` от `sent_at` (новая колонка) → `reason=incomplete` («первый вызов не завершился; проверьте по `client_order_id`; новая попытка — новый ключ») — `test_a_sent_record_that_never_completed_is_answered_as_incomplete`; `in_progress` старше guard перехватывается (ничего не отправлено, старый держатель отсечён) — `test_a_stale_unsent_claim_is_taken_over_and_its_holder_sends_nothing`, SQL — `test_a_stale_unsent_claim_is_reclaimed_a_sent_one_is_not`.
8. **`superseded`** говорит, что этот `client_order_id` не отправлялся, и называет `client_order_id` нового держателя (`IdempotencyRepository.current`) — проверяется в тесте п. 7.
9. **Отмена и сбои вокруг захвата:** `test_a_call_cancelled_while_its_claim_commits_releases_the_claim` (мутация: захват без shield — поймана), `test_a_failing_decision_transaction_releases_the_claim` (в фейке `fail_next_write`).
10. **Сериализация писателей в фейке** доказана тестом: `test_the_fake_database_serialises_writers[without_lock]` показывает потерянное обновление (два победителя), `[with_lock]` — один.
11. **`order_repeat` в журнале** (держатель, `client_order_id`, clientInfo, `replay|in_progress`), без обращений к бирже — `test_a_repeat_is_journaled_without_any_exchange_call`.
- **Решение оркестратора: вызов с ключом тоже пишет fingerprint.** Захватывается в той же транзакции, если свободен («тень»: fencing отправки — только по ключу, тень обновляется по `keeps_record`); консультируют fingerprint только вызовы без ключа. Тесты `test_a_keyed_call_then_the_same_call_without_a_key_places_one_order`, `test_keyed_calls_never_consult_the_fingerprint` (мутации: тень не берётся / вызов с ключом консультирует fingerprint — пойманы). Из-за тени снят `unique(action_id)` в миграции 0007 (ещё не в main). PLAN ADR-014 «Тикет 012» обновлён (пункты 1, 4, 6, 9, 12).

### Ревью, раунд 2 (APPROVE с 4 minor, исправлено 2026-11-03)
Каждое исправление проверено временной мутацией; все пойманы (скрипт: замена в коде → прогон → возврат файла).
1. **Тень вызова с ключом истекла во время простоя.** `_decide` → `_keep_shadow`: если `mark_sent(shadow)` не прошёл, в той же транзакции `claim(shadow, now)` свежей записью и, если получен, `mark_sent`; иначе тень остаётся у держателя. Тест `test_a_keyed_call_stuck_past_the_guard_takes_its_fingerprint_again` (вызов с ключом стоит перед решением дольше `IN_FLIGHT_GUARD`, во время его отправки идентичный вызов без ключа → `in_progress`, одна отправка; мутация «не захватывать снова» → две отправки).
2. **Повтор без ключа неизвестного исхода, сохранённого вызовом с ключом:** при ответе из fingerprint подсказка «тот же ключ вернёт этот ответ» заменяется на «без ключа повтор позже поставит НОВЫЙ ордер». Тест `test_a_keyless_repeat_of_a_keyed_unknown_outcome_is_told_a_later_repeat_is_a_new_order`.
3. **Проигравший повтор с ключом не трогает fingerprint** — `test_a_keyed_repeat_that_loses_its_key_never_touches_the_fingerprint` (мутация «убрать `return held, _Claims()`» поймана: свободный fingerprint оставался `in_progress` и блокировал вызов без ключа).
4. **Тесты дедлайнов падают быстро, а не виснут.** Хелпер `tests/fakes.py::call_with_watchdog`: через 2 с сторож отпускает `hold` и тест падает с «the bound under test did not fire» (shield не пускает внешнюю отмену, поэтому `anyio.fail_after` в тесте не помогал). Переведены `test_a_read_back_that_never_answers_is_fill_unknown`, `test_a_lookup_that_never_answers_is_bounded`, `test_a_send_that_never_answers_hits_the_overall_deadline_and_is_looked_up`; мутации «убрать `move_on_after`/`fail_after`» падают за ~2 с.
- PLAN ADR-014 «Тикет 012» (12): вызов с ключом, заставший fingerprint занятым, оставляет его держателю — повтор без ключа получает ответ держателя (известно, безопасно).
- **Локальные БД:** миграция 0007 менялась в ревью 1 (снят `unique(action_id)`, добавлена `sent_at`) под тем же номером ревизии. База, мигрированная веткой до ревью 1, этих изменений не получит: пересоздать её: удалить файл БД (и `-wal`/`-shm`) и выполнить `guarded-exchange init` заново (откат ревизии наш CLI не предоставляет). В main 0007 ещё не попадала.
