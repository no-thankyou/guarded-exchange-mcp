# 007: Ключи биржи: шифрование, CLI, проверка прав
Статус: IN_REVIEW
Зависит от: 004, 005
Требования: FR-30, FR-31, FR-49, FR-29 (часть: soft-delete)

## Цель
Пользователь через CLI добавляет, заменяет и удаляет ключ биржи; ключ хранится зашифрованным (AES-256-GCM, AAD, HKDF); права проверяются по allowlist (D-24), с веткой FR-49 по результату спайка 004.

## Scope
- `infrastructure/crypto.py`: keyring, HKDF-подключи (`credentials`, `audit`, `request_state`, `telegram`, D-14), AAD `credential_id‖user_id‖exchange`.
- Таблица `exchange_credentials` с environment, permissions, `permissions_checked_at`, `admin_attested`, status active/deleted (D-12, D-9).
- Use case `AddCredential`/`ReplaceCredential`/`DeleteCredential` (soft-delete); проверка прав: allowlist, `readOnly` → профиль чтения, `expiredAt`, предупреждение без IP whitelist.
- Ветка «права проверить нельзя»: testnet — только с `admin attest` в CLI (журнал), mainnet — отказ (SPEC FR-49, GP-3).
- Перепроверка прав: при старте и перед изменяющим действием, если старше 1 ч (хук для 011); расширение прав → `credentials_permissions_changed`.
- Подписанные запросы Bybit (HMAC-SHA256) в адаптере; ввод ключа в CLI без эха; секреты не попадают в логи/журнал.
- Allowlist адресов биржи (решение пользователя 2026-10-28, из ревью 001): `bybit_base_url` — только известные хосты Bybit по https (mainnet, demo, testnet); произвольный хост или http — только с явным тестовым флагом конфига. Иначе `ConfigError`, fail closed до первого подписанного запроса.
- Проверка master key при старте `serve` (перенесено из ревью 005, m5): `FileMasterKeyStore.exists()` уже отвергает права шире 0600, симлинк и битый ключ; `serve` должен загружать ключ до старта MCP и fail closed.

Решения и отклонения (2026-10-28, исполнитель):
- **Allowlist прав — одна таблица в домене** `PERMISSION_ALLOWLIST` (`domain/credentials.py`): `{"bybit": {"ContractTrade.Order", "ContractTrade.Position", "Spot.SpotTrade"}}`, строки `"Group.Name"`. Строго по D-24; **`Derivatives.DerivativesTrade` не добавлен** (открытый вопрос пользователю). Если нужен — одна строка в таблице плюс правка `test_permission_allowlist_is_exactly_d24` (тест-описание фиксирует таблицу целиком). `readOnly=1` не освобождает от allowlist: read-only ключ с `Wallet.*` тоже отклоняется (NFR-1). Ключ без прав вообще (`readOnly=0`, групп нет) проходит с профилем trade, но торговать им нечем — безопасно.
- **Имена прав с неожиданными символами** адаптер превращает в `<unrecognised>`: их нет в allowlist, ключ **отклоняется**, а не уходит в ветку «проверить нельзя» (иначе мусорный ответ открыл бы путь к attest).
- **Ветка FR-49 «проверить нельзя»** = `ExchangeUnavailable` от адаптера (сеть, таймаут, 5xx, 404 эндпоинта, неожиданный формат, 10002). Ключ, который биржа явно не приняла (10003/10004/10005/10007/10010/33004), — `exchange_credentials_invalid`, attest не помогает. `--admin-attest` применяется **только** если права проверить нельзя; если биржа ответила, решает её ответ, и ключ хранится как проверенный (`admin_attested=false`). Attest в CLI требует явного `y` на вопрос «NO withdrawal and NO transfer permission?» (или `--yes`); в журнале — `credential_added` с actor `cli:admin`, `attested_by`, `attestation`. Отклонённые ключи тоже журналируются (`credential_rejected`: причина, имена лишних прав, без ключа).
- **Среда ключа** = среда хоста `GX_BYBIT_BASE_URL` (`Settings.bybit_environment`). Пользователь другой среды получает `permission_denied` до того, как ключ куда-либо отправлен. Один сервер — одна среда (как уже для рыночных данных); ключи mainnet — вместе с переключением среды пользователя (027).
- **Перепроверка (D-24).** `RecheckCredential` пишет `credential_permissions_changed` только при изменении (`blocked`, `disallowed`). `RequireTradingCredential(user_id)` — хук для 011: перепроверка, если старше 1 ч; расширенные права → `credentials_permissions_changed`; истёк/нет ключа → `exchange_credentials_invalid`; read-only → `permission_denied`; устаревший ключ, который не удалось перепроверить, → `exchange_unavailable` (fail closed), кроме ключа на attest (его права и так не проверялись). Блокировка вычисляется из сохранённых прав, отдельного флага нет: вернулись права в allowlist — следующая перепроверка разблокирует. При старте `serve` — `RecheckActiveCredentials` фоновой задачей (не задерживает старт MCP; итог только в лог `credential_rechecked` / `credentials_recheck_failed`). При остановке сервера ей дают до 5 с закончить работу с БД: отмена посреди вызова aiosqlite оставляла поток, пишущий в закрытый event loop (поймано тестом с `-W error::PytestUnhandledThreadExceptionWarning`).
- **Профиль:** read-only ключ ограничивает **эффективную** политику в `application/policy._view` (`cap_profile`) — одна точка для `tools/list`, `tools/call` (`AuthorizeAccess`), `get_my_policy` и `policy show` (строка-примечание). Расширенные права профиль **не** режут: торговые инструменты остаются видимыми, а вызов получит конкретную причину `credentials_permissions_changed`, а не безликий `permission_denied`.
- **Хранение:** миграция **0006** `exchange_credentials` (+ `deleted_at`; частичный unique index `WHERE status='active'` по user+exchange+environment; CHECK длины nonce и «`deleted_at` ⇔ deleted»); 0001–0005 не тронуты, `schema.py` сверяется с миграциями существующим тестом. Шифротекст и nonce читает только `get_sealed`; списки ключей их не загружают. Soft-delete (D-9): строка остаётся; стирание шифротекста и аннулирование pending — вместе с pending (016/017).
- **Крипто:** `infrastructure/crypto.py` — `Keyring` (версии `{1: master}`), HKDF-SHA256 по назначениям `credentials|audit|request_state|telegram` (D-14), `AesGcmCredentialCipher` (nonce 96 бит, AAD с 4-байтовыми префиксами длины, открытый текст JSON, `CredentialUnreadable` без цепочки исключений). `FileMasterKeyStore.load()` читает через один `O_NOFOLLOW`-дескриптор и проверяет его `fstat` — проверяется тот же файл, который читается.
- **Секреты:** `ApiKeyPair` с `field(repr=False)` для обеих половин, `SealedSecret` тоже; `mask_secrets` маскирует `ApiKeyPair` целиком. DTO `query-api` разбирает только `readOnly/permissions/ips/expiredAt` (`apiKey`/`secret` отбрасываются `extra="ignore"`); ошибки разбора конверта и `query-api` поднимаются `from None`: pydantic цитирует вход, а вход содержит секрет. Сообщения валидации ввода называют поле, а не значение.
- **Подпись:** `infrastructure/bybit/signing.py`; для подписанного GET query строится один раз (`urlencode(sorted(...))`), подписывается и отправляется как есть; каждая попытка ретрая подписывается заново (свежий timestamp). Эталон — `tests/fixtures/bybit/signature_vectors.json`, посчитан OpenSSL независимо от кода (pybit не ставили). Время — системное (`now_ms`); синхронизации с `/v5/market/time` нет: при расхождении часов больше recv_window (5 с) биржа ответит 10002 → «проверить нельзя».
- **Allowlist хостов:** `infrastructure/bybit/hosts.py` (`api-demo`, `api-testnet` → testnet; `api.bybit.com`, `api.bytick.com` → mainnet), только https, порт 443, без пути/query/userinfo. **Отклонение от формулировки «произвольный хост — только с тестовым флагом»:** флаг `GX_TEST_ALLOW_LOOPBACK_BYBIT_URL` разрешает **только loopback** (127.0.0.1 / ::1 / localhost, http или https, любой порт); внешний неизвестный хост не разрешается ничем. Это строже и достаточно для тестов (AC говорит именно о loopback). Региональные хосты mainnet не добавлены (одна строка при необходимости).
- **Master key в `serve`:** проверяется после БД и до старта MCP: нет файла / права шире 0600 / симлинк / не 32 байта → exit 2, причина в stderr, stdout пуст. Команды `keys *` без пригодного ключа — exit 1 «cannot use the master key», к бирже ничего не уходит.
- **CLI:** `keys add|replace [--user] [--admin-attest] [--yes]` (ключ и секрет — `typer.prompt(hide_input=True)`), `keys delete [--user] [--yes]`, `keys show [--user]`. В выводе — id, среда, профиль, имена прав, срок, предупреждение про IP whitelist; ключ и секрет — никогда. `build_cli` получил обязательный `KeyCommands`.
- **Зависимость:** `cryptography>=50.0.2` объявлена явно (уже была в lock транзитивно от `mcp`; `uv lock --offline`); import-linter запрещает её в domain и application.
- Заметки добавлены в 008 (как брать ключ для чтения) и 011 (хук `RequireTradingCredential`, подпись POST).

Как потрогать руками: `uv run guarded-exchange init`, затем `uv run guarded-exchange keys add` (ввод без эха; текущий demo-ключ из спайка 004 будет отклонён с перечнем лишних прав, ключ только с Contract Orders/Positions + Spot Trade — принят), `keys show`, `policy show` (при read-only ключе — эффективный профиль read_only и примечание). Отказы конфигурации: `GX_BYBIT_BASE_URL=https://evil.example uv run guarded-exchange serve` → exit 2; `chmod 644` на master key → `serve` exit 2 (вернуть `chmod 600`).

- Отпечаток master key в БД (предложение из 005): сейчас подмена ключа обнаружится только как `CredentialUnreadable` при первом использовании.

- Региональные хосты Bybit (`api.bybit.kz`, `api.bybit.eu`, …) в `hosts.py` — по запросу.

Ревью, раунд 1 (CHANGES_REQUESTED, исправлено 2026-10-28):
- **M1.** `RequireTradingCredential` больше не отдаёт удалённый/заменённый ключ: домен `require_trading_allowed` отказывает для `status != active` (`exchange_credentials_invalid`, `reason=key_replaced_or_deleted`); результат перепроверки с неактивным ключом проходит через ту же проверку; секрет для торгового пути и перепроверки читается новым `CredentialRepository.get_sealed_active` (`status='active'` в SQL), `get_sealed` оставлен для разведки исхода (D-9). Тесты: `test_a_key_deleted_during_the_recheck_is_not_handed_out`, `test_a_key_replaced_between_the_check_and_decryption_is_not_handed_out`, `test_a_deleted_key_never_passes_the_trading_check`. В заметку 011 — финальная сверка под `lock_user` (D-8).
- m1. Исключение для attest при неудачной перепроверке — только пока `permissions is None` (ключ ни разу не проверялся); проверенный однажды ключ fail closed — `test_an_attested_key_verified_once_is_not_exempt_when_a_later_recheck_fails`.
- m2. Домен: `permissions is None` разрешено только при `admin_attested` и `environment is TESTNET`, иначе `permissions_unverified` — `test_unverified_permissions_pass_only_for_an_attested_testnet_key`.
- m3. Для кодов «ключ не принят» текст биржи не передаётся в `untrusted_text` (sign error эхом возвращает строку с API key) — тест с `origin_string[...]`.
- m4. Фоновая перепроверка при старте вынесена в `_serve_with_recheck`: при любой остановке (норма, исключение, отмена) ей даётся до 5 с в shielded scope, затем отмена — `test_a_failing_server_still_lets_the_start_up_recheck_finish` (предупреждения о потоках — ошибка).
- m5. `keys delete` и `keys show` работают без master key (только UoW + clock) — `test_keys_show_and_delete_work_without_a_usable_master_key`.
- m6. Master key открывается с `O_NONBLOCK`: FIFO → «not a regular file» без зависания — `test_load_refuses_a_fifo_without_blocking`.
- m7. Ошибки, скрывающие `ValidationError`/JSON/крипто-ошибки, создаются вне `except` (`_validated`, `_iso_time`, `_json_or_none`, `_try_open`): ни `__cause__`, ни `__context__` не ссылаются на исходную ошибку; тесты проверяют оба атрибута (в т.ч. не-JSON тело с секретом и `expiredAt` с секретом).
- **AAD включает environment** (D-12): `credential_id ‖ user_id ‖ exchange ‖ environment`; тест «testnet-ключ не открывается как mainnet»; ADR-009 поправлен. Данных ещё нет — миграция не нужна.
- README: read-only ключ с лишними группами прав тоже отклоняется — создавать ключ только с нужными правами.
- Предложение (не делалось, записано в PLAN «Риски»): MAC метаданных строки `exchange_credentials` (`permissions`, `admin_attested`, `status`, `environment`) подключом `credentials` — сейчас запись в БД в обход приложения может «разблокировать» ключ до ближайшей перепроверки.
