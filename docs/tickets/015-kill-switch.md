# 015: Kill switch
Статус: DONE
Зависит от: 011
Требования: FR-16, FR-44

## Цель
Пользователь (через MCP или CLI) и админ (CLI) включают kill switch: все действия, увеличивающие риск, запрещены, снижающие и чтение работают; снять — только через CLI, admin kill switch снимает только админ.

## Scope
- MCP `activate_kill_switch` (без rate limit, D-16); CLI `kill-switch on/off`, `admin kill-switch on/off`.
- Включение берёт `lock_user` (для TOCTOU с executor, D-8); событие в журнал.
- Проверка в `submit_action` для INCREASES; спот-ордер — всегда INCREASES (решение пользователя: строго).

## Non-scope
- Отмена pending при включении (018/017).

## Заметки
- Требование (SPEC FR-16, дословно): «Kill switch: пользователь (для себя) и админ (для любого) мгновенно запрещают все действия, **увеличивающие риск**; снижающие риск действия и чтение продолжают работать (с обычной политикой подтверждений). Включение kill switch само ничего на бирже не отменяет. Снять kill switch, включённый админом, может только админ.» Классификация — FR-43: «**увеличивающее риск** (новый ордер не reduce-only, увеличение плеча, изменение ордера в сторону большего объёма или менее выгодной цены) или **снижающее риск** (отмена ордера, reduce-only ордер, закрытие позиции, установка/изменение SL/TP, уменьшение плеча)». FR-44: «Через MCP агент может только **читать** свою эффективную политику и **включить** свой kill switch. Любое другое изменение политики … и снятие kill switch — только через служебный канал (CLI)». SPEC 8 (non-goal): автоматическая отмена ордеров при kill switch. GP-5: спот-ордер под kill switch остаётся увеличивающим риск (строго).
- Для 013/014: в транзакции решения (под `lock_user`, по свежему пользователю) вызвать `domain.kill_switch.require_allowed(policy.kill_switch, risk, action.kind)` с направлением риска действия (amend — относительно текущего ордера, плечо — относительно текущего); раннюю проверку — после проверки повтора, как в `_prepare`. Отказ `kill_switch_active` — `Outcome.REFUSED`.

### Итоги реализации (2026-11-03)
- **Хранение.** `users.kill_switch` (`none|user|admin`, `server_default 'none'`, CHECK) — миграция 0008 (`op.add_column` с колоночным CHECK: SQLite не добавляет табличный constraint без пересборки `users`, а пересборка конфликтует с внешними ключами на неё). `User.kill_switch`, порт `UserRepository.set_kill_switch`. В `EffectivePolicy.kill_switch` (PLAN 5.1) значение попадает через `load_policy_view`; это не настройка политики: его нет в потолке и overrides, `strictest()`/`settings_to_payload` его не трогают. `get_my_policy` показывает `kill_switch`, `policy show` — второй строкой.
- **Правила** (`domain/kill_switch.py`): одно состояние на пользователя (PLAN `none|user|admin`). Админ, включая поверх пользовательского, делает его `admin` (иначе пользователь снял бы то, что хочет админ); пользователь/агент поверх `admin` его не понижают; пользователь не снимает `admin` → `permission_denied` (`details.reason=admin_kill_switch`); админ снимает любой. `require_allowed` отказывает `kill_switch_active` (новый код ошибки в `domain/errors.py`, восстанавливается `restore_error`) только для `INCREASES`; `details`: `kill_switch`, `action`, `risk`; `next_step` перечисляет, что продолжает работать, и кто может снять.
- **Use cases** (`application/kill_switch.py`): `ActivateKillSwitch` (MCP, только включение) и `SetKillSwitch` (CLI, `by=user|admin`). Одна write-транзакция: `lock_user` → чтение пользователя под блокировкой → запись → `kill_switch_on|off` в журнал пользователя (`before`, `after`; агент — ещё `client`), actor `mcp:agent` / `cli:user` / `cli:admin`. Команда без изменения ничего не пишет и отвечает `changed: false`.
- **Путь ордера** (`submit_action.py`, две строки): (1) ранняя проверка в начале `_prepare` — после проверки повтора и до проверки ключа и чтений биржи; отказ журналируется `order_refused` со `stage: pre_check`, захват идемпотентности освобождается (как у прочих ранних отказов); (2) проверка в `_decide_locked` под `lock_user` по пользователю, перечитанному в транзакции решения (D-8), до плана и лимитов — включение между первыми проверками и решением блокирует отправку; отказ хранится для явного ключа (`REFUSED`, как отказ лимита). Почему ранняя проверка после повтора, а не рядом с профилем: повтор ордера, отправленного до включения, должен получить первый ответ (ордер есть), а не `kill_switch_active`, который агент прочтёт как «ничего не произошло».
- **MCP**: `activate_kill_switch` без аргументов, `Permission.READ` (видят все, включая read-only: остановить торговлю безопасно всегда), `idempotent_hint=true`, `destructive_hint=false`; ответ `{kill_switch: user|admin, changed}`. Rate limiter'а ещё нет (022); исключение D-16 — заметка для 022.
- **CLI**: `kill-switch on|off [--user]`, `admin kill-switch on|off [--user]`; `off` спрашивает подтверждение (`--yes`), без терминала — exit 1 и ничего не меняет; включение напоминает, что на бирже ничего не отменено. Отказ (`user` снимает `admin`) — exit 1 с сообщением, без traceback.
- Общие файлы затронуты точечно: `fakes.py` (+`set_kill_switch`), `schemas.py` (+поле `PolicyOut.kill_switch`, +`KillSwitchOut`), `server.py`/`access.py`/`bootstrap.py`/`tests/e2e/support.py` (+use case и инструмент), `test_cli.py` (`PolicySpy.kill_switch`), `test_policy_storage.py` (`PolicyCommands.kill_switch`), `test_mcp_stdio.py` (+`activate_kill_switch` в списке инструментов read-only пользователя).
