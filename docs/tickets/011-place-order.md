# 011: place_order насквозь (testnet, без HITL)
Статус: IN_REVIEW
Зависит от: 006, 008, 009
Требования: FR-4, FR-10, FR-13, FR-14, FR-15, FR-17, FR-25 (заглушка), FR-36 (часть), FR-43 (PlaceOrder), FR-48 (граница цены), ADR-010

## Цель
Агент размещает market/limit ордер на споте и перпетуалах (reduce-only для перпетуалов) на testnet: правила инструмента, округление объёма вниз, notional по худшей цене, лимиты, allowlist, классификация риска, Limit IOC для market, журнал attempt/outcome. Подтверждение — заглушка: если политика требует подтверждения → `confirmation_channel_unavailable` (fail closed); «без подтверждения» — только явной настройкой админа.

## Scope
- Domain: `money.py` (округление: объём вниз, цена не по tick — ошибка, SPEC GP-1), `actions.PlaceOrder`, `risk.classify`, reduce-only clamp, `limits.check_limits` (FR-13, FR-14, FR-15).
- ADR-010: worst = best × (1 ± slippage), округление в безопасную сторону, `Limit IOC`; фактически исполненный объём — чтением после отправки (D-15).
- `submit_action.py` — единый путь: auth → rules → policy/limits → confirm-заглушка → execute; D-10 (без I/O в транзакции); `action_id` → `client_order_id = gx-…` (D-19).
- Журнал: отказ лимита (FR-17), attempt до отправки, outcome после; самоописание клиента по итогам 002 (FR-36).
- Торговые инструменты доступны только на testnet (в v1 — всегда, mainnet/027 — v2); ошибки ADR-013 для торговли.
- Правила инструмента для **нетрадуемых** инструментов (из ревью 009): `instruments-info` без `status` отдаёт только `Trading`/`PendingOpen` (linear), т.е. для делистингуемого/`Delivering`/`Closed` перпетуала `get_instrument_rules` сейчас даст `not_found`. Reduce-only закрытие позиции на таком инструменте (FR-43, FR-15) не должно упираться в `not_found`: решить здесь — запрашивать с явным `status` или без фильтра правил для снижающих риск действий; новые увеличивающие риск ордера по-прежнему только при `status=trading`.
- Денежные аргументы (`qty`, `price`, …) публикуются строкой с pattern по образцу `DecimalStr` (а не дефолтным `anyOf: [number, string]` для `Decimal`), чтобы модель не слала float (D-4, спайк 002). Самоописание клиента для FR-36 — `ctx.session.client_params.client_info` (может быть `None`).

## Non-scope
- Идемпотентность и неизвестный исход (012), другие действия (013, 014), kill switch (015).

## Заметки
- Из 008: префикс `orderLinkId` системы — одна константа `CLIENT_ORDER_ID_PREFIX = "gx-"` в `infrastructure/bybit/mapper.py`, по ней `order_origin` помечает ордера `system/external`; формат `client_order_id` (D-19, ≤ 36 символов Bybit) строить от неё. Сверка `system` с журналом отправленных ордеров (FR-2: префикс — только быстрый фильтр) — в 011/012, когда такие записи появятся.
- Из спайка 004 (2026-10-28, demo): на perp (по умолчанию, `lpaPerp=false`) биржа **молча сдвигает цену любого limit-ордера**, выходящего за коридор `GET /v5/market/price-limit`, к границе коридора (`linear_create_over_buy_limit_default*`); на spot — отказ `170193`, в режиме reject на perp — `110121`. Решить в тикете: (1) обычный limit вне коридора — ошибка до отправки (как SPEC GP-1, «цена — ошибка») или сдвиг с явным сообщением агенту; (2) для market (Limit IOC, ADR-010) — ограничение коридором на стороне сервера. В любом случае цена, показанная в FR-21 и записанная в журнал, должна совпадать с ценой ордера на бирже (читать `price` из ордера после отправки).
- Из 007: перед любым изменяющим действием вызывать `application.credentials.RequireTradingCredential(user_id)` — он перепроверяет права ключа, если последняя проверка старше 1 ч (D-24), отказывает `credentials_permissions_changed` / `exchange_credentials_invalid` / `permission_denied` (read-only ключ), при невозможности перепроверить устаревший ключ — `exchange_unavailable`, а если перепроверку отбил rate limit биржи — `rate_limited` с `retry_after_s` (оба fail closed, `details.reason=permissions_recheck_failed`), и возвращает расшифрованный `ApiKeyPair` для адаптера. Подписанные запросы — `infrastructure/bybit/signing.signed_headers`; для POST подписывать ровно отправляемое тело (`json.dumps(..., separators=(",", ":"))`), вектор POST уже есть в `tests/fixtures/bybit/signature_vectors.json`. Хук не закрывает гонку целиком: между ним и отправкой ордера `keys replace/delete` может успеть — финальная сверка (ключ всё ещё `active`, тот же `credential_id`) под `lock_user` в той же write-транзакции, где пишется `attempt` (D-8, D-10: без сетевого I/O внутри); ключ с `status != active` хук уже не отдаёт (`key_replaced_or_deleted`).

### Итоги реализации (2026-10-29)
- По заметке спайка 004: (1) обычный limit вне коридора `price-limit` — `instrument_rule_violation` до отправки (`details.rule=price_band`, граница в `max_price`/`min_price`), сдвига нет; (2) market — `Limit IOC` по `worst`, ограниченной коридором на стороне сервера (только улучшает цену); цена в ответе и в `order_outcome` — из ордера на бирже (`price_source: exchange`), пока ордер не виден — отправленная (`request`). Остальные решения (FR-14 через текущее плечо символа, reduce-only без min notional, `status=Delivering` для снижающих риск, коды ответов POST) — PLAN, ADR-010, «Тикет 011».
- Нетрадуемые инструменты: для reduce-only правила ищутся с `any_status` (адаптер повторяет `instruments-info` с `status=Delivering`, только linear); разрешены статусы `trading` и `settling`, новые увеличивающие риск ордера — только `trading`. `Closed` по-прежнему `not_found` (торговать на нём нельзя).
- Ошибки ввода (правила инструмента, `position_not_found`) отвечаются до решения и не журналируются; решение политики (`order_refused` | `order_attempt`) — в одной write-транзакции под `lock_user` с повторной проверкой пользователя, ключа (тот же `credential_id`, `active`), профиля и лимитов на свежей политике.
- Тесты, где был заглушечный `place_order` (`tests/e2e/test_mcp_policy.py`, `tests/integration/test_http_auth.py`), переименованы на `stub_trade`: имя теперь занято настоящим инструментом.

### Ревью, раунд 2 (CHANGES_REQUESTED, исправлено 2026-11-03)
Каждый новый тест проверен временным внесением мутации (все мутации пойманы):
1. **Сбой журнала после неудачной отправки.** Запись `order_outcome` на путях `unknown`/`not_sent`/`rejected`/`BaseException` — через `_try_journal_outcome`: ошибка БД уходит в лог (`order_outcome_not_recorded`), агент получает исходную ошибку (`outcome_unknown` с `client_order_id`, а не `internal_error`, после которого он мог бы отправить ордер ещё раз). Тесты `tests/unit/test_submit_action_review2.py`: `test_a_journal_failure_after_an_unknown_outcome_still_answers_outcome_unknown`, `test_a_journal_failure_after_a_definite_failure_keeps_the_exchange_error[not_sent|rejected]`; в фейке — хук `FakeTrading.during_place`.
2. **Коды неизвестного исхода.** `UNKNOWN_OUTCOME_RET_CODES` дополнен spot 170001, 170007, 170032, 170234 и UTA 3400214 («Server error, please try again later»), сверено с https://bybit-exchange.github.io/docs/v5/error (2026-11-03). Других серверных/таймаут-кодов для linear (кроме уже учтённых 10000, 10016) в документации нет; `429` («high server load, please retry») и 110079 (ордер в обработке — относится к amend/cancel) не добавлены: биржа просит повторить, т.е. запрос не принят. Строки в `test_a_possibly_sent_order_is_unknown_and_never_retried`. Решение оркестратора: явный список в v1, «unknown по умолчанию для изменяющих POST» — предложение в заметках 012.
3. **Окно отмены между коммитом `order_attempt` и shield.** `_decide` тоже под `CancelScope(shield=True)` (короткая транзакция с `busy_timeout`), а перед ним `checkpoint_if_cancelled()`: отмена до решения соблюдается, закоммиченная попытка всегда доходит до отправки и `order_outcome`. Фейк БД при `checkpoint` теперь уступает циклу и после коммита (как реальный драйвер), хук `InMemoryDatabase.after_commit`. Тесты `test_a_cancellation_right_after_the_attempt_commits_still_sends_and_records_the_outcome`, `test_a_call_cancelled_before_the_decision_decides_and_sends_nothing`.
4. **Ошибки чтения биржи перед решением** (`exchange_unavailable`, `rate_limited`, `unsupported_position_mode`, `not_found` при известном principal) журналируются `order_refused` со `stage: pre_check`; ошибки ввода (`invalid_params`, в т.ч. инструмент не в USDT, `instrument_rule_violation`, `position_not_found`) — по-прежнему нет. PLAN «Тикет 011» (5) обновлён. Тесты `test_an_unavailable_exchange_before_the_decision_is_journaled`, `test_hedge_mode_and_an_unknown_instrument_are_journaled`, `test_input_errors_found_while_reading_and_planning_are_not_journaled`; в фейке — `FakeTrading.position_error`.
5. **Произведения в контексте вызывающего.** `money.exact_product` и `money.shift_by_pct` считают в собственном `localcontext` (prec 80); `worst_price`, `notional`, `order_value` — через них. Тесты `tests/unit/test_order_domain_review2.py` (`prec = 4` у вызывающего).
6. Общий дедлайн POST под shield — не делалось, заметка «Из ревью 011» в тикете 012.
