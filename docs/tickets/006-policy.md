# 006: Политика: потолок, ужесточение, get_my_policy
Статус: IN_REVIEW
Зависит от: 005
Требования: FR-11, FR-12, FR-18, FR-19 (поля), FR-23 (поля), FR-42 (поля), FR-44, FR-45

## Цель
Эффективная политика пользователя = strictest(потолок админа, настройки пользователя) по полям (D-23); CLI для админа и пользователя; агент читает свою политику через MCP `get_my_policy`; ослабление отклоняется.

## Scope
- Domain `policy.py`: `AdminCeiling`, `UserOverrides`, `EffectivePolicy`, `strictest`, `validate_override`; дефолты testnet/mainnet (PLAN раздел 6) и нового пользователя (FR-45).
- Таблица `policies`, репозиторий, use cases `ReadPolicy`, `SetCeiling` (admin), `TightenPolicy` (user); всё в журнал.
- CLI (typer): `policy show`, `admin policy set-ceiling`, `policy tighten`.
- MCP `get_my_policy` (только чтение, FR-44); проверка профиля в одном месте application (FR-11) — `permission_denied`.
- Фильтрованный `tools/list` по профилю (ADR-012, спайк 002): `GuardedMCPServer.list_tools()` скрывает торговые инструменты от read-only; principal — `get_access_token()` / локальный пользователь; набор разрешённых инструментов даёт application.

## Non-scope
- Kill switch (015), mainnet-переключение (027).

## Заметки
- Из 005: `lock_user` на SQLite — no-op (сериализацию даёт `BEGIN IMMEDIATE` write-UoW; вне write-UoW он падает). Значит, на SQLite «блокировка пользователя» = блокировка всей БД на время write-транзакции: держать их короткими, без сетевого I/O (D-10). Ветка Postgres (`FOR UPDATE`) — в 028.

Решения и отклонения (2026-10-28, исполнитель):
- **Domain `policy.py`:** `PolicySettings` (13 полей) → `AdminCeiling`, `EffectivePolicy` (+ `environment`); `PolicyPatch` (все поля необязательны, `UNSET` — «не трогать», потому что `None` — реальное значение порога) = `UserOverrides` и одновременно запрос изменения. Для каждого поля одно правило «строже из двух» в таблице `_RULES`; им же считается и `strictest`, и проверка ослабления: `new` не слабее `current` ⇔ `stricter(current, new) == new` — правила не могут разойтись. Там же проверки жёстких границ (slippage ≤ 3%, TTL 1..600 с, плечо ≥ 1, `max_pending` 0..100, деньги — только конечный `Decimal`, float/bool отвергаются) и codec в canonical JSON (журнал и хранилище).
- **Уточнение D-23 (PLAN 5.1 и раздел 12 поправлены в раунде 1):** D-23 говорит «окна — min», но для окна FR-46 строже **более длинное** окно (тот же лимит действий считается за больший период), поэтому `unconfirmed_window_s` — max. Остальные числа — min.
- **Правило подтверждения — два плоских поля:** `confirm_actions` (множество, объединение) и `confirm_above_notional_usdt` (порог, min; `None` = выключен = +∞). `ActionKind` вынесен в `domain/actions.py` (011 добавит туда сами действия). Длительности — целые секунды (`confirmation_ttl_s`, `unconfirmed_window_s`): так же в журнале, CLI и `get_my_policy`. Allowlist — `category:SYMBOL` (`linear:BTCUSDT` ≠ `spot:BTCUSDT`).
- **`validate_override` сравнивает с текущей эффективной политикой, а не с потолком:** `policy tighten` никогда ничего не ослабляет, в том числе собственные прежние настройки пользователя. Trade-off: вернуть свою настройку назад нельзя (только админ поднимет потолок — но override всё равно останется строже). Предложение ниже.
- **Хранение:** миграция **0004** (`policies`: `user_id` PK/FK → users, `ceiling` TEXT NULL, `overrides` TEXT, `updated_at` epoch ms), 0001–0003 и триггеры журнала не тронуты. Нет строки / `ceiling IS NULL` = дефолтный потолок для среды пользователя **из кода** — пользователям из 005 не нужна data-миграция, `tighten` без потолка админа не «замораживает» дефолты. Trade-off: изменение дефолтов в коде меняет потолок ненастроенных пользователей (они всё равно read-only). Upsert одной командой `ON CONFLICT DO UPDATE`.
- **Журнал:** `policy_ceiling_set` (actor `cli:admin`, payload `changes` + полный `ceiling`) и `policy_tightened` (actor `cli:user`, `changes` + полная `effective`) — в цепочке пользователя (`chain_id = user_id`), в той же write-транзакции. Отказ ничего не пишет (транзакция откатывается).
- **Порт `UnitOfWork.lock_user`** добавлен (SQL — `dialect.lock_user`, fake записывает вызовы): `SetCeiling`/`TightenPolicy` — read-modify-write строки политики, на Postgres (028) без блокировки два изменения потеряли бы одно. Use cases вызывают его первым после поиска пользователя.
- **Application `policy.py`** (вместо `read_policy.py` + `admin.py` из PLAN 3 — четыре тесно связанных use case в одном модуле): `ReadPolicy` (`for_principal` для MCP — неизвестный/отозванный → `permission_denied` с одним и тем же текстом; `by_name` для CLI → `not_found`), `SetCeiling`, `TightenPolicy`, `AuthorizeAccess` (`visible(user_id, {tool: Permission})`, `require(user_id, Permission)`) — **единственное место проверки профиля (FR-11)**. Политика читается на каждом вызове: изменение видно на следующем `tools/list`/`tools/call` без переподключения (тест).
- **Interface, минимальный слой (для merge с 009):** `interface/mcp/access.py` — `TOOL_PERMISSIONS` (имя инструмента → `READ|TRADE`), `PrincipalProvider` (локально `fixed_principal(user.id)`, резолвится при старте `serve`; в 026 — `get_access_token().subject`) и `ToolGate`, который только применяет ответ `AuthorizeAccess`. `server.py`: `PolicyScopedServer(MCPServer)` с двумя override (`list_tools` фильтрует, `call_tool` до `super()` спрашивает `ToolGate.refusal`). **При merge 009:** перенести эти два метода в `GuardedMCPServer`, проверка прав — **до** обработки ошибок валидации (отказ не раскрывает схему аргументов; тест `bad_args` это фиксирует). `create_server` теперь требует `principal`, `UseCases` — `read_policy` и `authorize`.
- **Fail closed:** инструмент без записи в `TOOL_PERMISSIONS` скрыт и отклоняется (`permission_denied`), тест реестра требует, чтобы все зарегистрированные инструменты были объявлены. `get_ticker` требует `READ`: без активного principal не работает ничего.
- **E2E скрытого торгового инструмента:** торговых инструментов ещё нет (011), поэтому тест регистрирует заглушку `place_order` на настоящем сервере и объявляет её `TRADE` через параметр `create_server(tool_permissions=...)`; проверяется, что тело не выполнилось.
- **CLI:** `policy show [--user]`, `policy tighten` (локальный пользователь), `admin policy set-ceiling [--user]`; общий набор опций (`--profile`, `--allow` повторяемый / `--allow-none`, `--max-order-notional-usdt`, `--max-leverage`, `--slippage-pct`, `--confirm KIND|all|none`, `--confirm-above-notional-usdt X|none`, `--confirmation-ttl-s`, `--[no-]trust-client-ui`, `--[no-]prefer-external-channel`, `--unconfirmed-max-actions`, `--unconfirmed-window-s`, `--max-pending`). Плохое значение — exit 2 с именем настройки; отказ use case (ослабление, нет пользователя, пустое изменение, не инициализирована БД) — exit 1, причина и подсказка в stderr, без трейсбека. Вывод — таблица «потолок / настройка пользователя / эффективное».
- **Для 011/015/017:** торговые use cases обязаны сами вызывать `require_permission(policy, Permission.TRADE)` (gate в MCP — только один вход; у executor и CLI-approve своего gate нет) и при перепроверке FR-48 брать `strictest(...)` заново. Новые инструменты — в `TOOL_PERMISSIONS`.
