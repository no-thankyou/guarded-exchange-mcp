# 027: Отзыв доступа, mainnet и изоляция (AC-2)
Статус: TODO
Зависит от: 026, 017
Требования: FR-29, FR-32, FR-33, AC-2, D-22

## Цель
Отзыв доступа действует немедленно и аннулирует ожидающие подтверждения; админ включает mainnet пользователю (локально — только с флагом `allow_local_mainnet`); два пользователя работают одновременно без доступа к данным друг друга.

## Scope
- Use case `RevokeAccess` под `lock_user`: PENDING/APPROVED → CANCELLED, EXECUTING/UNKNOWN доводятся (D-9).
- `admin user set-env mainnet` + дефолтный потолок mainnet (FR-18); локальный режим — отказ без `allow_local_mainnet`, журнал.
- Снятие ограничения «торговля только на testnet» из 011 — теперь по политике/среде.

## Non-scope
- Postgres (028).

## Acceptance criteria
- [ ] E2E (HTTP): AC-2 — два пользователя с разными политиками одновременно; read-only не торгует; чужие pending/ордера/журнал → `not_found`.
- [ ] Unit (edge case): подтверждение после отзыва → не исполнено; EXECUTING доведён до исхода.
- [ ] Unit: mainnet в локальном режиме без флага → отказ; с флагом — предупреждение в журнале.

## Заметки
- Из 006 (ревью): потолок в `policies` не привязан к среде. Хранимый потолок (`ceiling` не NULL), выставленный админом на testnet (например, 1000 USDT, x10, `trust_client_ui=true`), после `set-env mainnet` продолжит действовать на mainnet, нарушая инвариант FR-18 «mainnet строже». Ненастроенный пользователь (`ceiling IS NULL`) получает дефолт mainnet автоматически. Решить при переключении среды: сбросить потолок к дефолту mainnet (с записью в журнал), хранить потолок по среде (`policies(user_id, environment)`) или требовать явный `set-ceiling` перед переключением. Overrides пользователя (только строже) переносить безопасно.
- Из ревью 026: отзыв токена/пользователя проверяется на каждом HTTP-запросе, но **не обрывает уже открытые долгоживущие потоки** (SSE-ответ, идущий `tools/call`, legacy GET-поток сессии, `subscriptions/listen`): они живут до конца. Решить здесь: закрывать сессии/потоки отозванного principal (реестр активных потоков по `user_id`) или документировать границу; для pending это закрывает аннулирование + перепроверка FR-48 в executor.
