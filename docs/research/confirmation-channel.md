# Research: внешний канал подтверждения человеком

Дата исследования: 2026-10-27. Исследователь: сабагент `researcher` (фаза Explore).

## 1. Вопрос и затронутые требования

SPEC, раздел 9, пункт 4: какой внешний канал подтверждения (вне чата, модель его не контролирует) использовать в v1. Кандидаты: Telegram-бот с inline-кнопками, одноразовая ссылка на веб-страницу сервера, web push / ntfy, email, CLI `approve <id>`, TOTP-код. Дополнительно: как устроено состояние «ожидает подтверждения» (FR-47), кто исполняет действие после подтверждения и что при рестарте сервера.

Затронутые требования: FR-20 (подтверждает человек, не модель), FR-21 (точные параметры показаны человеку), FR-22 (привязка к действию и параметрам, одноразовость, без подмены), FR-23 (TTL 2 мин, максимум 10), FR-24 (отказ), FR-25 (fail closed без доверенного канала), FR-29 (отзыв доступа аннулирует pending), FR-42 (внешний канал доверен всегда; на mainnet UI клиента не доверяется по умолчанию), FR-47 (два исхода, сервер исполняет сам), FR-48 (перепроверка на момент исполнения), FR-27 (результат неизвестен), FR-36 (журнал: кем/когда/каналом), NFR-1, NFR-2 (CI без сети), NFR-6 (запуск одной командой, GIF), AC-1, AC-4.

Ключевая мысль, вокруг которой построен отчёт: FR-21 требует, чтобы параметры показывала человеку доверенная сторона. Всё, что проходит через чат, пересказывает модель — она может исказить параметры (ошибка или prompt injection). Значит внешний канал должен (1) сам рендерить параметры из серверного состояния, (2) аутентифицировать человека фактором, которого нет у модели, (3) принимать решение по уникальному идентификатору pending-записи, а не по данным из чата.

## 2. Факты (с источниками, проверено 2026-10-27)

### 2.1 Telegram Bot API
- Актуальная версия Bot API — 10.3 от 2026-08-24 (предыдущие: 10.2 — 2026-07-14, 10.1 — 2026-06-11). Источник: https://core.telegram.org/bots/api (Recent changes), проверено 2026-10-27.
- `InlineKeyboardButton.callback_data` — «1-64 bytes». `CallbackQuery` содержит `from` (User, отправитель — заполняет Telegram), `message` (сообщение бота с кнопкой), `data`. Нажатие inline-кнопки не отправляет сообщение в чат; на `callback_query` бот должен ответить `answerCallbackQuery` (иначе у клиента крутится индикатор). Источники: https://core.telegram.org/bots/api, https://core.telegram.org/bots/features, проверено 2026-10-27.
- Получение обновлений: long polling `getUpdates` (параметр `timeout` — «Timeout in seconds for long polling», по умолчанию 0 = short polling) или webhook. Обновления «stored on the server until the bot receives them ... but they will not be kept longer than 24 hours». Long polling нельзя использовать, пока установлен webhook. Источники: https://core.telegram.org/bots/api, https://core.telegram.org/bots/faq, проверено 2026-10-27.
- Webhook: только HTTPS, порты 443, 80, 88, 8443; валидный сертификат (self-signed — загрузкой через `certificate`); заголовок `X-Telegram-Bot-Api-Secret-Token` (1–256 символов `A-Za-z0-9_-`) для проверки, что запрос от Telegram. Источники: https://core.telegram.org/bots/api, https://core.telegram.org/bots/faq, проверено 2026-10-27.
- Лимиты отправки: в один чат — не больше ~1 сообщения в секунду (короткие всплески допустимы, иначе 429); в группу — 20 сообщений в минуту; массово — ~30 сообщений/с без paid broadcasts. Источник: https://core.telegram.org/bots/faq, проверено 2026-10-27. Для нас (одно сообщение на pending + одно редактирование) запас огромный; FR-46 и rate limits FR-34 и так ограничивают частоту торговых действий.
- Deep linking: `https://t.me/<bot>?start=<param>`, параметр до 64 символов `A-Za-z0-9_-`, рекомендован base64url; бот получает `/start <param>`. Источник: https://core.telegram.org/bots/features, проверено 2026-10-27.
- Не проверено (из памяти, проверить в реализации): при одновременных `getUpdates` двух процессов с одним токеном Telegram возвращает 409 Conflict; у `CallbackQuery` нет собственного поля времени нажатия (есть только `message.date` исходного сообщения) — значит время решения фиксируется по часам сервера при обработке.

### 2.2 Python-библиотеки для Telegram
- `aiogram` 3.31.0, выпущен 2026-08-26 (3.30.0 — 2026-07-17), `requires_python >=3.10,<3.15`, «Supports Telegram Bot API 10.3». Полностью asyncio. Источник: https://pypi.org/project/aiogram/, https://pypi.org/pypi/aiogram/json, проверено 2026-10-27.
- `Dispatcher.feed_update(bot, update)` — «Main entry point for incoming updates», `feed_raw_update(bot, dict)` — то же из сырого dict; `start_polling(*bots, polling_timeout=10, handle_as_tasks=True, ...)`, `handle_signals` по умолчанию True (при встраивании в процесс сервера нужно выключить, чтобы бот не перехватывал SIGINT/SIGTERM), `stop_polling()`. Источник: https://docs.aiogram.dev/en/latest/dispatcher/dispatcher.html, проверено 2026-10-27. `feed_raw_update` позволяет тестировать обработчики без сети, подсовывая JSON update; исходящие вызовы Bot API в тестах нужно подменить (custom session / mock) — конкретный механизм проверить по странице Testing aiogram при реализации.
- `python-telegram-bot` 22.8, выпущен 2026-06-12, `>=3.10`, поддерживает Bot API 10.0 (отстаёт от актуальной 10.3). Источник: https://pypi.org/project/python-telegram-bot/, проверено 2026-10-27.

### 2.3 MCP: URL-mode elicitation (связано с вариантом «ссылка»)
- В спецификации MCP 2026-07-28 elicitation имеет режимы `form` и `url`; URL mode — «out-of-band interactions that must not pass through the MCP client»; запрос доставляется внутри `InputRequiredResult` (multi round-trip requests), клиент ретраит исходный вызов, сервер по `requestState` или своему состоянию решает, завершено ли взаимодействие. `action: "accept"` в URL mode означает лишь согласие открыть URL, а не завершение. Пометка: URL mode «may change in future protocol revisions». Источник: https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation.md, проверено 2026-10-27.
- Требования к серверу: «MUST NOT provide a URL which is pre-authenticated to access a protected resource, as the URL could be used to impersonate the user by a malicious client»; «MUST verify the identity of the user who opens the URL»; «MUST bind elicitation requests to the client and user identity»; HTTPS вне dev. Клиент «MUST open the URL ... in a secure manner that does not enable the client or LLM to inspect the content or user inputs» — но это обязанность клиента, которой сервер проверить не может. Источник тот же.
- Следствие для нас: сама спецификация MCP прямо запрещает «одноразовую ссылку-капабилити, по которой достаточно перейти». Любая ссылка, проходящая через клиента, видна клиенту и потенциально модели; страница должна сама аутентифицировать человека.

### 2.4 ntfy
- Action buttons: `view`, `broadcast` (Android), `http`, `copy`; до трёх действий; `http` по умолчанию шлёт POST, поддерживает `headers` и `body`. Приоритеты 1–5. Источник: https://docs.ntfy.sh/publish/, проверено 2026-10-27.
- «Obviously all topics on ntfy.sh are public»; без настроенного доступа топик — это фактически пароль; защищённые топики — Basic auth / access token. Источник тот же. Сквозное шифрование в разделе publish не упомянуто.
- Не подтверждено официальной документацией: что `http`-действие отправляет само приложение на устройстве (а не сервер ntfy). Если так — устройство должно иметь сетевой доступ к нашему серверу (публичный URL или LAN).

### 2.5 Claude Code: модель с Bash на той же машине
- Sandboxed Bash в Claude Code: запись ограничена рабочей директорией и temp, но «Reads are allowed across most of the machine, including credential files like ~/.ssh and ~/.aws/credentials»; sandbox покрывает только Bash/PowerShell/Monitor, «File tools, MCP servers, and hooks still run directly on the host»; сеть через proxy с изначально пустым allowlist доменов. Permissions и sandbox — разные слои. Источник: https://code.claude.com/docs/en/sandboxing, проверено 2026-10-27 (копия на docs.claude.com устарела).
- Следствие: в AC-1 через Claude Code у модели может быть shell на той же машине, где работает локальный сервер. Любой канал, доверие к которому основано на «локальной машине» (CLI-команда, localhost-страница без второго фактора, файл с секретом), модель потенциально может использовать сама: запустить `approve`, сделать `curl localhost`, прочитать БД/секрет. Это главный риск для CLI и локальной веб-страницы.

### 2.6 Email, web push, TOTP
- Отдельные первоисточники не проверялись: решения по ним принимаются из архитектурных свойств (нужен SMTP и публичный URL для ссылки; web push требует Service Worker, VAPID и HTTPS-origin; TOTP по RFC 6238 — код не привязан к параметрам действия). Если какой-то из этих вариантов будет выбран — версии библиотек (`aiosmtplib`, `pywebpush`, `pyotp`) нужно проверить отдельно.

## 3. Варианты с trade-offs

Общий механизм привязки для всех каналов (FR-22, FR-23): на сервере есть pending-запись `{id (128 бит случайности), tenant_id, action, canonical_params, params_hash, env, created_at, expires_at, status}`. Канал показывает человеку параметры, отрендеренные сервером из этой записи (не текст модели). Решение — это атомарный переход `PENDING → APPROVED/REJECTED` с условиями `now < expires_at`, `tenant` совпадает с аутентифицированным в канале человеком, `status == PENDING` (compare-and-set, одноразовость). Исполняется ровно `canonical_params` из записи — агент не передаёт параметры повторно, поэтому подмена между запросом и исполнением невозможна по построению; `params_hash` фиксируется в журнале и проверяется перед отправкой на биржу. HMAC-подпись параметров нужна только для stateless-ссылок; поскольку FR-47 всё равно требует серверного состояния, достаточно случайного id + серверной записи, HMAC — опционально (например, в callback_data для защиты от подбора, хотя 128 бит случайности этого и так не допускают).

### A. Telegram-бот, inline-кнопки Approve / Reject
- Привязка к человеку: Telegram сам заполняет `callback_query.from.id`, модель подделать его не может (у неё нет Telegram-аккаунта человека). Сервер проверяет `from.id == linked_telegram_user_id` для tenant и что чат приватный. Привязка аккаунта (pairing): пользователь пишет боту `/start`, бот отвечает одноразовым кодом, пользователь вводит его в CLI `guarded telegram link <code>` (CLI показывает, какой Telegram-аккаунт привязывается, и просит подтвердить). Обратный порядок (CLI выдаёт deep link `t.me/<bot>?start=<token>`) тоже возможен (токен ≤64 символов base64url), но тогда утечка ссылки (например, если модель с shell её увидит) позволит привязать чужой аккаунт — поэтому код от бота → CLI безопаснее.
- Привязка к действию: `callback_data = "a:<pending_id>"` / `"r:<pending_id>"` (128-битный id в base64url — 22 символа, укладывается в 64 байта). После решения бот редактирует сообщение (убирает кнопки, пишет «Approved 12:01:33» / «Expired»), повторное нажатие → CAS не проходит → «уже обработано». По истечении TTL фоновый таймер редактирует сообщение в «Expired».
- Может ли модель нажать сама: нет — нажатие возможно только из Telegram-клиента человека; ссылка/кнопка в контекст модели не попадает; агент получает только `pending_id` и статус. CSRF неприменим (нет браузерной сессии). Остаточный риск: в локальном режиме модель с shell может прочитать токен бота — это даёт ей возможность читать/воровать updates и слать сообщения от имени бота, но не сфабриковать callback с `from.id` человека. Однако модель с shell может напрямую изменить локальную БД (status=APPROVED) — это риск не канала, а локального режима целиком (см. раздел 4).
- Сеть: long polling не требует публичного URL — работает и локально (за NAT), и в multi-tenant (один бот на сервис, много пользователей различаются по `from.id`). Webhook нужен только для масштабирования; в v1 не нужен. В multi-instance деплое polling должен вести ровно один процесс (иначе конфликт `getUpdates` — не проверено, см. 2.1).
- Сложность: средняя. Нужен токен бота от @BotFather (секрет, хранится как ключи биржи), исходящий доступ к api.telegram.org, pairing-команда в CLI.
- Лимиты: несущественны для нашего объёма (2.1).
- Тестируемость без сети: порт `ConfirmationChannel` + fake в unit/интеграционных тестах; адаптер aiogram тестируется через `feed_raw_update` с подменённой сессией Bot; ручной набор — против настоящего Telegram.
- Демо GIF: лучший вариант. Split screen: слева Claude Desktop/Code, справа Telegram Desktop (или веб) — появляется карточка ордера с параметрами, клик Approve, в чате агент видит результат. Визуально объясняет «подтверждение вне чата» без слов.
- Минусы: внешняя зависимость (доступность Telegram в сети пользователя, аккаунт Telegram), секрет-токен бота, сторонний сервис видит параметры ордеров (инструмент, объём — не ключи; для портфельного проекта приемлемо, документировать).

### B. Одноразовая ссылка на веб-страницу сервера (HTTP endpoint)
- Привязка: ссылка `/confirm/<pending_id>`; страница рендерит параметры из записи; Approve/Reject — только POST с CSRF-токеном; GET ничего не меняет (иначе prefetch, превью ссылок или `fetch`-инструмент модели «нажмут» сами).
- Может ли модель перейти: если ссылка попала в tool result или в URL-mode elicitation — она видна клиенту/модели. По спецификации MCP ссылка не должна быть pre-authenticated (2.3), значит страница обязана аутентифицировать человека: логин в веб-сессию (в v1 нет веб-интерфейса — non-goal), WebAuthn/passkey (сильно, но сложно) или TOTP на странице (модель не знает секрет, если не может прочитать его с диска). В локальном режиме страница на localhost доступна `curl` из shell модели — без второго фактора защиты нет.
- Сеть: локально — localhost (телефон не достучится); multi-tenant — нужен публичный HTTPS URL и, по сути, веб-аутентификация пользователей.
- Плюсы: нет сторонних сервисов; естественно сочетается с URL-mode elicitation (2.3) — клиент сам предложит открыть ссылку. Минусы: требует аутентификации человека в вебе, CSRF, HTTPS, а сила гарантии в локальном режиме зависит от второго фактора. Для v1 дороже Telegram при более слабой гарантии.
- Демо: нормально (браузер рядом с чатом), но хуже читается как «вне контроля модели».

### C. ntfy (или web push)
- ntfy: уведомление с `http`-кнопками Approve/Reject, по нажатию — POST на наш сервер. Аутентификации нажавшего нет: решает тот, кто знает URL (капабилити) или подписан на топик; на ntfy.sh топики публичны, топик = пароль (2.4). Нужен сетевой доступ телефона к нашему серверу (публичный URL/LAN), и, вероятно, запрос шлёт приложение на устройстве (не подтверждено). Привязка к человеку слабее, чем у Telegram (нет `from.id`), сторонний сервер видит параметры, если не self-host. В локальном режиме модель с shell может прочитать URL из сообщения/конфига и дернуть его.
- Web push: Service Worker, VAPID, HTTPS-origin, подписка из браузера — по сути веб-интерфейс, который в non-goals. Не для v1.

### D. Email
- Ссылка в письме → те же проблемы, что у B (нужна аутентификация на странице), плюс SMTP-конфигурация, задержка доставки (TTL 2 минуты под угрозой), спам-фильтры, сканеры ссылок в почтовых сервисах делают GET (ещё одна причина «только POST»). Демо — слабое. Не рекомендуется.

### E. CLI `guarded approve <id>`
- Привязка: CLI читает pending-запись из хранилища, печатает параметры, спрашивает `y/N`, делает CAS. Аутентификация человека — только «имеет доступ к терминалу/ОС-пользователю».
- Может ли модель сама: в Claude Code — да, если у модели есть Bash и доступ к той же машине/данным: `guarded approve <id> --yes` или `echo y | guarded approve <id>`. Проверка TTY (`isatty`) отсекает тривиальные пайпы, но обходится через `script`/pty. Защита возможна только конфигурацией вне нашего контроля (deny-правило permissions на команду, sandbox с запретом чтения каталога данных) — а sandbox Claude Code по умолчанию разрешает чтение почти всей машины (2.5). В Claude Desktop (без shell) риск ниже, но не нулевой при других MCP-серверах с доступом к shell.
- Для remote multi-tenant CLI — это служебный канал админа (раздел 2 SPEC), пользователю он не подходит без SSH-доступа.
- Плюсы: ноль внешних зависимостей, тривиально тестируется, удобен для CI-сценариев и разработки. Минусы: по SPEC «внешний канал считается доверенным всегда» (FR-42) — CLI этому определению в общем случае не соответствует.

### F. TOTP-код
- Вариант «человек вводит код в чат, модель передаёт его в `confirm(id, code)`»: модель не может сгенерировать код, но (1) параметры человек видит в пересказе модели — нарушение FR-21; (2) код не привязан к параметрам — модель может применить подсмотренный код к другому pending в окне 30 с (смягчается: код одноразовый и действует только на один, самый старый pending); (3) появляется инструмент подтверждения в MCP, что противоречит духу FR-20/AC-4. Не рекомендуется как канал.
- Как второй фактор внутри B (код вводится на странице, не в чат) — допустим, но это уже часть варианта B.

## 4. Рекомендация

Основной внешний канал v1 — Telegram-бот с inline-кнопками, long polling, библиотека `aiogram` 3.31.x (актуальна под Bot API 10.3; `python-telegram-bot` 22.8 отстаёт до 10.0). Причины: единственный из кандидатов, где решение принимается на устройстве и в аккаунте, которых нет у модели, а `from.id` удостоверяет Telegram; не нужен публичный URL ни локально, ни в multi-tenant; бот рендерит параметры из серверной записи (FR-21); лучший кадр для GIF (AC-1, NFR-6).

Второй минимальный канал — CLI `approve/reject <id>`, но с явной пометкой в политике: канал `cli` считается доверенным только если админ это включил (по умолчанию — выключен для mainnet и вне локального режима), а README честно пишет, что при агенте с shell на той же машине (Claude Code) CLI не даёт гарантии AC-4. Внутри кода нужен fake-канал `InMemoryConfirmationChannel` для тестов — он, а не CLI, основа CI. Альтернатива второму каналу на будущее — веб-страница с WebAuthn, как цель URL-mode elicitation (2.3); в v1 не делать.

Предлагаемые порты (для PLAN): исходящий порт `ConfirmationChannel` (`async notify(pending_view)`, `async notify_resolved(pending_id, outcome)`), реализации `TelegramChannel`, `CliChannel` (no-op уведомление, человек сам вызывает CLI), `FakeChannel`. Входящие решения из любого адаптера идут в один use case `ResolveConfirmation(pending_id, decision, channel, human_identity)` в application-слое; MCP-адаптер этот use case не вызывает вовсе (структурная гарантия AC-4, проверяемая тестом: в реестре MCP-инструментов нет ничего, что ведёт к `ResolveConfirmation`, плюс e2e-тест «агент пытается подтвердить»). FR-25: при создании pending, если у tenant нет ни доверенного UI клиента (FR-42), ни привязанного внешнего канала — отказ сразу, не создавая записи.

Как работает «ожидает подтверждения» (FR-47) — предложение для PLAN:
- Состояния записи: `PENDING → APPROVED → EXECUTING → EXECUTED | FAILED | UNKNOWN`; ветки `PENDING → REJECTED | EXPIRED | CANCELLED` (отзыв доступа/смена ключей, FR-29). Все переходы — CAS в хранилище в одной транзакции с записью журнала (FR-36: канал, `human_identity`, время по часам сервера).
- Исполнитель — фоновая asyncio-задача в процессе сервера (`ConfirmedActionExecutor`): адаптер канала после успешного APPROVED будит её (in-process очередь), а при старте и периодически она сканирует хранилище на `APPROVED` (паттерн outbox, чтобы не потерять сигнал). Перед отправкой — полная перепроверка FR-48 (права, доступ, kill switch, лимиты, allowlist, граница цены), затем `EXECUTING` с детерминированным `client_order_id`, производным от `pending_id` — это даёт идемпотентность на бирже и разведку при FR-27.
- Повторный вызов агента с тем же ключом идемпотентности/параметрами возвращает тот же `pending_id` и текущий статус, не создаёт второго действия (FR-26, FR-47). Статус — read-инструмент `get_confirmation_status(id)`.
- Рестарт: `PENDING` с неистёкшим TTL остаются (кнопки в Telegram продолжают работать; updates хранятся у Telegram до 24 ч, поэтому нажатия во время простоя будут доставлены после старта, но решаются по серверному времени — если TTL истёк, «Expired»); истёкшие помечаются `EXPIRED` и сообщение редактируется. `APPROVED` (не начатые) — исполняются, только если не прошло больше короткого execution deadline (предлагаю: не позже `expires_at` исходного запроса; иначе `EXPIRED_AFTER_APPROVAL`, агенту и журналу — причина), чтобы сервер, лежавший час, не исполнил ордер по устаревшему решению; FR-48 дополнительно защищает ценой. `EXECUTING` при старте — результат неизвестен: сверка с биржей по `client_order_id` (FR-27) и переход в `EXECUTED`/`FAILED`/`UNKNOWN`.
- Multi-instance (remote): Telegram-polling и executor должны работать в одном экземпляре (leader) или в отдельном процессе-воркере; для v1 достаточно одного процесса сервера — зафиксировать как ограничение.

Главные риски:
- Локальный режим + агент с shell (Claude Code): модель может читать/менять локальное хранилище и секреты в обход любого канала. Это не решается выбором канала; варианты для PLAN — запуск сервера в Docker/от другого ОС-пользователя с данными вне досягаемости агента (NFR-6 «одна команда в контейнерах» это поддерживает), рекомендация deny-правил/sandbox Claude Code в README, tamper-evident журнал (FR-50) как обнаружение, а не предотвращение. Нужно явно вписать в threat model README.
- Зависимость от Telegram: доступность сети/аккаунта у пользователя; при недоступности — fail closed (FR-25), это корректно, но демо зависит от сети.
- Привязка Telegram-аккаунта (pairing) — новая поверхность атаки; делать «код от бота → ввод в CLI» с подтверждением имени аккаунта, отвязка — только CLI, журналировать.
- Секрет токена бота хранить так же, как ключи биржи (FR-31), не логировать.

Что остаётся неизвестным / проверить в реализации или другими исследованиями:
- Поведение `getUpdates` при двух одновременных потребителях (409 Conflict) и отсутствие времени нажатия в `CallbackQuery` — подтвердить по полному тексту Bot API.
- Механизм подмены сетевой сессии `Bot` в тестах aiogram (страница Testing документации aiogram) — проверить при реализации адаптера.
- Поддерживают ли Claude Desktop / Claude Code URL-mode elicitation и как MRTR (`InputRequiredResult`) сочетается с pending (FR-47) — вопрос отдельного исследования (SPEC раздел 9, пункты 2–3); от ответа зависит, стоит ли в v2 делать веб-страницу как цель URL elicitation.
- Кто отправляет `http`-действие ntfy (устройство или сервер) — не подтверждено; для рекомендации не критично.
- Нужно ли поддерживать несколько внешних каналов на одного пользователя одновременно (первое решение побеждает по CAS) — решение для PLAN.
